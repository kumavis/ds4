# C1: where single-token decode compute time goes, and what can cut it

Branch `c1-compute-profile` (worktree `/data/ds4-c1`), based on `kumanix-int`
(6e69e59). Unless stated otherwise, runs use:

* the native MXFP4 model on two drives (`DS4_ROCM_STREAM_REPLICA`), with the
  automatic cache;
* `--rocm --ssd-streaming --temp 0`;
* the code prompt with `--nothink`.

Every number comes from `/data/ds4-bench/results.jsonl` and the run logs in
`/data/ds4-bench/runs/<UTC>-<tag>/run.log`. Any number that was not measured
is marked "estimate" or "modelled".

## 1. Bottom line

* **The 66.8 ms of non-read time per plain MXFP4 token is mostly memory
  bandwidth.**
  * One decode step reads **12.94 GB of weights**: 8.43 GB dense (Engram read
    as its exact E4M3 repack) and 4.51 GB of routed experts (byte inventory in
    section 4).
  * The GPU reads at most **241 GB/s** (measured, section 4), so the bytes
    alone take **53.6 ms**. That is 80 % of the 66.8 ms.
  * The weight-streaming kernels reach 150 to 225 GB/s, which is 62 to 93 % of
    that peak.
* **Launch overhead and synchronisation are small.**
  * The GPU idles only about 0.8 ms per token at the per-layer drain and the
    router-id readback.
  * The host enqueues about 4.6 ms per token of launches, and that time runs
    ahead of the GPU.
  * Small, latency-bound kernels take about 12 ms per token: HC mixing,
    norms, rope, compressor, indexer and the attention core.
* **Plain single-token decode at native precision cannot reach 20 tok/s on this
  machine.** Even with zero read wait and perfect kernels, 12.94 GB at
  241 GB/s gives 18.6 tok/s. To halve compute, fewer bytes must be read per
  generated token, in one of two ways:
  * dense Q8 weights at about 4 bits, which changes numerics;
  * rows sharing each weight read, as in the DSpark verify or batching.
* **Reductions that keep the output bitwise identical are worth about 2 %, below
  the brief's 3 % bar.** So the stop condition applies: section 7 gives the
  ranked list. Two cheap ones are implemented, bitwise equal (kernel test and
  all five gates) and on by default:
  * load-pipelined RMS norms (`DS4_ROCM_C1_NORM`);
  * a wider-load HC projection (`DS4_ROCM_C1_HC_PROJ`).

  Together they **measure** as follows:
  * -2.1 ms of GPU time per token;
  * MXFP4 code 8.46 / 8.46 to **8.59 / 8.62 tok/s (+1.7 %)**;
  * prose +2.0 %;
  * Q2 +2.8 % (one run each);
  * DSpark unchanged.
* **The largest remaining bitwise candidate is the Engram E4M3 projection.** It
  takes about 3.4 ms per token for 316 MB, about 92 GB/s. At 200 GB/s it would
  save about 1.9 ms (estimate). It is not implemented.
* **Why Q2 is no cheaper.** Both models read the same 8.4 GB of dense weights.
  On MXFP4, D2 runs about 9.9 ms of expert compute while the host waits for
  reads, so that time is counted as wait. What stays exposed is about 12-13 ms
  of expert compute per token on both models (section 6).
* **Deviation from the brief: the model has 40 layers, not 43** (`C1T`
  inventory). Experts are therefore 40 x 6 x 17.93 MiB = 4.51 GB per token.

## 2. Method

### Instrumentation (`DS4_ROCM_C1_PROF`, off by default)

Files: `ds4_c1_prof.h`, `rocm/ds4_rocm_c1_prof.cuh`, marks in `ds4.c`
(`C1M`/`C1F`) and in `routed_moe_mxfp4_decode_overlap_launch`.

**How marks work.** Marks sit at component boundaries of the single-token
step `ds41_graph_step`:

* embed;
* per layer: draft capture and Engram upload; HC norm, projection and
  Sinkhorn; HC sum and attention norm;
* attention: q_a+kv pair, q_b and norms, rope/kv write, compressor,
  indexer+top-k, attention core, output a/b;
* post-attention HC; router; shared expert;
* host wait for router ids and cache lookup;
* routed: plan and x quantize, resident gate/up, read wait, missing gate/up,
  fused down; or the all-resident path;
* MoE finish, HC expand, layer drain;
* quiesce, vocab head, logits readback.

A mark closes the segment that started at the previous mark.

**Cost when off.** One load and a branch per mark: `c1-off-code-r1/r2` ran at
8.48 and 8.47 tok/s, against the reference 8.45-8.47.

**Modes.**

| mode | what a mark does | cost (code, tok/s) |
|---|---|---|
| `coarse` | host time only, at marks that already follow a device drain (layer end, logits) | 8.46 (`c1b-prof-coarse-off`), i.e. none |
| `events` | also records a timing `hipEvent` on the null stream; no sync. GPU time per segment = elapsed between consecutive events | 8.26 (`c1b-prof-events-off`): +3.1 ms/token |
| `sync` | `hipDeviceSynchronize` before every mark: host time = isolated latency of each segment | 7.63 (`c1b-prof-sync-off`): +12.6 ms/token |

**Prefill exclusion.** Prefill on this path also uses single-token steps.
Only steps that end with a logits readback count, so the stage B and C
profiles are decode-only (507 tokens; the first 4 are skipped).

**Read wait.** The read-wait counter (`g_stream_read_profile_wait_us`) is
sampled at every mark, so each segment's host time splits into read wait and
the rest.

**Other evidence.**

* **Bytes.** At startup the profiler prints the weight inventory: the name,
  type and bytes of every tensor a step can touch (`C1T` lines).
* **Kernel tests.** `tools/c1/c1_exact.cpp`, model-free: candidate kernels
  against verbatim copies of the kernels they replace. It compares bitwise on
  random inputs and times 200 launches each; weights are cycled through enough
  copies to exceed L2. It is built with the ds4 ROCm flags (`-O3 -ffast-math`).
* **Bandwidth and launch costs.** `tools/c1/c1_membw.cpp`, model-free.
* **DSpark verify.** The existing sync-bracketed
  `DS4_ROCM_DSPARK_V41_VERIFY_PROFILE` (pre-attention, attention,
  post-attention, MoE and head per verify call), plus a new `C1 verify
  rdwait=` line per call.
* **DSpark plain steps.** `DS4_D8_STEP_TRACE`.

### How much the instrumentation inflates (code, decode-only, same binary 95bd7cb)

| run | ms/token (graph step) | read wait ms | non-read ms | vs uninstrumented |
|---|---:|---:|---:|---:|
| `c1b-prof-coarse-off` | 118.13 | 51.38 | 66.76 | baseline |
| `c1b-prof-events-off` | 120.70 | 50.85 | 69.85 | +3.1 (+4.6 %) |
| `c1b-prof-sync-off` | 130.69 | 43.51 | 87.18 | +20.4 (+31 %) |

**Why sync mode is so much higher.** Bracketing every segment with a drain:

* adds about 1,200 synchronisations per token;
* removes D2's overlap: the resident gate/up can no longer run under the read
  wait. As a result less time is counted as read wait and more as compute.

The summed sync-bracketed segments overstate non-read time by 31 %. The
events numbers below are therefore the primary breakdown. Sync mode was used
to check them: each component's sync time equals its events GPU time plus
about 3-25 µs per segment, so the GPU deltas are real kernel time and not
queueing artefacts.

## 3. Breakdown: plain MXFP4 decode, per token (`c1b-prof-events-off`)

### How to read the table

* **GPU ms** is the elapsed time between null-stream events: what the GPU
  spent on that segment.
* **Bytes** are weight bytes read per token, from the `C1T` inventory, summed
  over the 40 layers.
* **GB/s** = bytes / GPU time.

The GPU column adds up to the 120.67 ms step span. Of that:

* 40.98 ms is GPU idle while the host waits for reads;
* 9.87 ms of expert work runs inside the host read wait (resident gate/up and
  part of the down).

Non-read wall time is therefore 79.69 - 9.87 = 69.8 ms. That is 66.8 ms
uninstrumented: multiply the rows by about 0.956 (estimate).

### Per layer

`/data/ds4-bench/c1-layers-events-off.txt` holds the `C1L` rows. Non-read GPU
time is 1.75-1.97 ms per layer, and 3.44 / 3.69 ms in the two Engram layers
(1 and 14). This is consistent with D5's fitted A = 1.4 ms before the router.

### Host-side work

* **Enqueue.** Host enqueue per token (the host column of non-blocking
  segments) is about 4.6 ms, so the host stays ahead of the GPU.
* **Waits.** The host waits for the GPU at three points per layer: the router
  event, the read wait and the layer drain. Plus once at the logits.
* **Router-id readback and cache bookkeeping.** `sel_wait_host` is 42.4 ms of
  host time per token. Almost all of it is waiting for the GPU to finish
  attention, router and shared expert. The GPU itself idles only 0.12 ms in
  that segment, so the readback and cache bookkeeping (lookup and starting the
  reads) are hidden behind the shared expert.
* **Plan and pointer tables.** `moe_prep_xq` takes 0.29 ms host and 0.41 ms
  GPU.

### Kernel launches

* **Cost per launch (microbench).**
  * An empty kernel costs 0.65 µs host and 1.71 µs GPU, back to back.
  * Launch plus `hipDeviceSynchronize` is a 6.8 µs round trip.
  * A sync `hipMemcpy` D2H of 24 B takes 5.8 µs.
* **Launch count per token: not measured.** Two indirect bounds:
  * the total GPU idle is 0.84 ms;
  * every latency-bound segment together (HC, rope, compressor, indexer,
    attention core) is about 11.9 ms.

  So launch and dispatch overhead is at most a fraction of that 11.9 ms, which
  is mostly single-block kernel latency.

## 4. GPU read bandwidth (`tools/c1/c1_membw.cpp`, `/data/ds4-bench/c1-membw.log`)

| test | GB/s |
|---|---:|
| streaming read, `hipMalloc` 64 MiB to 4 GiB (best grid) | 241-243 |
| same, 4 x unrolled loads | 235-241 |
| expert-like gather: 40-43 layers x 6 random 18.8 MB chunks from a 4 GiB pool | 239-244 |
| `hipHostMalloc` 1 GiB | 236 |

LPDDR5X-8000 on a 256-bit bus is 256 GB/s theoretical, so the GPU reaches
94 % of it.

The decode kernels read packed weights; nothing is expanded on the decode path:

* **MXFP4 experts.** 17 bytes per 32 weights. The x and mid activations are
  Q8_K-quantized and the dot runs on the packed nibbles.
* **Dense Q8_0.** 34 bytes per 32. The F16 expansion cache
  (`cuda_q8_f16_*`) is not used by the single-token path.
* **Engram.** E4M3 at 1 byte plus 1/32 per weight (the exact repack).
  Confirmed by `DS4_ROCM_V41_ENGRAM_E4M3_TRACE`: "usable=1 bytes=157900800".

66.8 ms of non-read time. Of the 79.7 ms of GPU work, 9.9 ms is hidden under
read waits.

## 5. What bounds compute

**Memory bandwidth, then kernel latency.**

* **The bandwidth floor.** Weight bytes per token at peak bandwidth take
  53.6 ms. The bandwidth-heavy rows of the table take 66.0 ms of GPU time at
  76-93 % efficiency: attention projections, router, shared, routed, head,
  Engram.
* **The remaining GPU time.** About 12 ms is single-block or few-block
  kernels (HC, rope, compressor, indexer, attention core). About 0.8 ms is
  sync bubbles. Host-side work is hidden.

**The hypothesis in the brief holds,** with these corrections: 40 layers,
4.5 GB of experts, and 8.4-8.7 GB of dense weights that outweigh the experts
2:1.

**What could cut bytes touched:**

* Dense Q8 weights at about 4.25 bits (MXFP4 or Q4) instead of 8.5:
  -3.79 GB. This changes numerics.
* Router F32 to BF16: -157 MB. Changes numerics.
* Vocab head at 4 bits: -350 MB, included in the first item. Changes
  numerics.
* Amortising the dense weights over several rows, as DSpark verify does.

## 6. Q2 and DSpark

### Q2 (`c1b-q2-prof-events-off`, IQ2_XXS/Q2_K experts, 9.95 MB per expert)

* The dense GPU work is the same as MXFP4's, within 1 %: attention 2.37 +
  9.35 + 15.78, shared 8.15, router 1.89, head 3.13, HC and Engram the same.
* The routed experts take 12.31 ms GPU for 2.39 GB, about 194 GB/s.
* Q2 has no D2 overlap. The host waits for all missing experts (18.9 ms, in
  the `moe_prep_xq` segment) before any expert kernel runs, so all 12.3 ms of
  expert compute counts as non-read time.
* MXFP4's experts cost 22.75 ms of GPU time, but 9.9 ms of it runs during the
  read wait. The exposed part, about 12.9 ms, matches Q2's 12.3 ms.
* Result: non-read time is 69.0 ms for Q2 and 69.8 ms for MXFP4 (events).
  Uninstrumented: Q2 rest 66.0 ms against 66.8 ms.
* On Q2 the experts are a smaller share; dense is about 80 % of the bytes.

### DSpark (MXFP4 code, `DS4_DSPARK_SCHED=old`, `c1b-dsp-prof-off`)

Run totals: 10.87 tok/s, 172 rounds, 340 accepted drafts, decode_misses
8,165, matching `c1b-dsp-off` and `int-mx-code-old`. The tokens of the
DSpark runs were not checked against plain decode.

**The 512 tokens break down as:**

* **107 verify calls**, average 4.72 rows (sync-bracketed profile, 104 after
  the first 3):
  * 331 ms per call: 231 ms read wait and **100 ms non-read**;
  * the 100 ms splits into pre-attention (HC, norms, Q/KV projections)
    20.3 ms, attention 31.5 ms, post-attention 3.1 ms, MoE non-read 44.5 ms
    (router, shared, union of up to 30 experts per layer), post-MoE 0.9 ms;
  * by rows: 2 rows 82 ms non-read, 3 rows 85 ms, 4 rows 92 ms, 6 rows
    113 ms;
  * sync-bracketed, so an overestimate of perhaps 5-10 % (estimate).
* **65 plain steps inside the session:** 135.5 ms each, 69.8 ms read wait and
  65.7 ms non-read (`D8_STEP`).
* **Drafter:**
  * 2,164 ms in total for 107 proposals: 20.2 ms per proposal;
  * 394 draft tokens: 5.5 ms per drafter token step, not split further;
  * not sync-bracketed.

**Non-read time per generated token** = (107 x 100 + 65 x 65.7 + 2,164)
/ 512 = **33.5 ms**, close to the brief's estimate of about 34 ms. Read wait
per generated token is about 57 ms.

**What this shows.** Each extra verify row adds about 8 ms of non-read time
(82 ms for 2 rows, 113 ms for 6). One single-token step costs 66 ms. The dense weights are read once per call, and that is the
saving.

## 7. Ranked reductions

| # | reduction | gain per token | basis | keeps output? | status |
|---|---|---:|---|---|---|
| 1 | Dense Q8_0 to about 4.25-bit (attention, shared, head) | -3.79 GB, about -16 to -18 ms (-25 %) | modelled at 205-241 GB/s | **no** | not implemented; needs an accuracy decision |
| 2 | Bitwise-equal rewrites that bring every weight-streaming kernel to about 95 % of peak (attention out/q_b/q_a, shared, router, experts) | about -8 ms GPU (upper bound) | modelled from section 3 | yes, if bitwise | Q8 attempt failed (row 6); not pursued further |
| 3 | Engram E4M3 projection, 92 to about 200 GB/s | about -1.9 ms (-2.8 %) | estimate (kernel share of the 3.45 ms not isolated) | yes, if bitwise | not implemented |
| 4 | **Load-pipelined RMS norms**: HC norm 20480 plus the weighted 5120/1280/512 norms (`DS4_ROCM_C1_NORM`) | -1.2 ms modelled; **measured -1.9 ms GPU** (with row 7, section 8) | microbench: 16.4 to 3.5 µs x 80, 7.0 to 4.8 µs x 80, 3.5 to 3.0 µs x 40, 2.8 to 2.6 µs x 40 | **yes** (bitwise, kernel test + gates) | **adopted, default on** |

| 6 | Q8 matvec load pipelining (`DS4_ROCM_C1_Q8_PIPE`) | 0 to +8 % per kernel in the microbench; 8.43-8.45 vs 8.47-8.48 tok/s in the model | measured | **no**: `-ffast-math` reassociates the per-block dot differently | default off |
| 7 | **HC projection, 128-element loads per lane** (`DS4_ROCM_C1_HC_PROJ`) | -0.17 ms modelled; measured -0.24 ms GPU | microbench 10.2 to 8.1 µs x 80 | **yes** | **adopted, default on** |
| 8 | Router F32 to BF16 | -0.8 ms | modelled | no | not implemented |
| 9 | Parallel 16-thread HC Sinkhorn | slower (3.3 to 4.3 µs) | microbench | no (iterated divisions round differently) | rejected, not in the tree |

Rows 1 and 8 change floating-point results. Per the brief they were not
adopted and are given as modelled effects only.

## 10. Not verified / caveats

* The C1 profile covers plain decode on code. Prose, hash and long were
  gated and timed but not profiled.
* The kernel launch count per token was not measured.
* For the Engram add, the split between the E4M3 projection and its norms was
  not measured, so the 92 GB/s is for the whole segment.
* The DSpark numbers come from sync-bracketed verify calls; no events profile
  ran on the verify path. The drafter step was not broken down. DSpark output
  equality was not checked.
* The bandwidth floor assumes every byte is read from DRAM once per token:
  the weights are far larger than the L2 and the infinity cache.
* The kernel exactness test compares on random inputs. On the model, the
  gates are the evidence.
