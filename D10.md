# D10: read bandwidth vs tok/s (drive count), and what the drafter's memory holds

Branch `d9-dspark-economics`, scripts `scripts/d10/`, outputs `scripts/d10/out/`
(`d10a.txt` full tables, `d10a.json`, `d10b.txt`, `bytecmp.json`, GGUF tables).
**No new binary and no benchmark runs.** One data read ran under the GPU lock:
the byte-compare in Part B (0.33 GB, `/data/ds4-bench/d10-bytecmp.log`).
**Every tok/s figure in Part A is modelled** (an estimate), except where it is
labelled "measured".

## Bottom line

* **A third internal Gen4 drive: modelled +10..+16 % for DSpark** (old or
  model scheduler, mean of five prompts, kumanix-int cache) **and +7..+11 %
  for plain decode.** Anchored to today's measurements, that is about
  12.5-13.3 tok/s for DSpark code (10.9 today) and 9.2-9.6 for plain code
  (8.45 today).
* **USB4 adds little and is uncertain.** With a USB4 enclosure added to three
  internal drives, the modelled DSpark gain is +13..+22 %; with two, +11..+27 %.
  The low end is no better than three internal drives: the low case assumes
  the vendor 3.6 GB/s is not reached and that two enclosures share one
  controller.
* **With the larger int2 cache, each drive is worth about 1.5-2 points
  less.** int2 has fewer misses per verified row (18.7-26.1 vs 22.5-30.9). A
  third drive gives +9..+14 % for DSpark on int2.
* **Scaling method: the per-miss cost is almost all bandwidth, and
  existing measurements support this.** The fitted marginal cost per expert
  miss is 1.37-1.49 ms. Moving one MXFP4 expert at today's reader rate takes
  1.446 ms (18.80 MB at 13.0 GB/s). Existing D1 runs measured one vs two
  drives with the same binary and the same tokens. Pure bandwidth scaling
  reproduces that measured change within ±2 % for plain code, plain prose and
  DSpark code.
  * This is a test of scaling down to one drive. Scaling up to 3-5 drives is
    an extrapolation.
  * Three or more drives also need a code change: replica support takes
    exactly two files. Each extra drive also needs its own copy of the
    model (501.6 GB for MXFP4).
* **Q2 reads from one drive today** (it has no replica). A second drive
  holding a Q2 replica is modelled at +11..+13 % for DSpark and +7..+9 % for
  plain. Three drives give about +14..+17 % for DSpark.
* **Part B: no drafter tensor is a copy of a main-model tensor**, and no
  host copy is kept after upload.
  * The drafter has no vocabulary head or embeddings of its own; it already
    uses the main model's.
  * The only output-neutral saving that is certain is the original Markov
    head `markov_w2`: 0.123 GiB that is loaded but never read (estimate
    +0.015 tok/s).
  * The big item is the drafter's 6.72 GiB of routed experts. 84 % of the
    drafter is resident, yet each proposal touches at most 15 of the 128
    experts per stage.
  * Moving them into the streamed expert cache would free up to 6.7 GiB,
    worth +0.8 tok/s gross at D4's 0.12 tok/s per GiB (estimate). The net
    value depends on how often the drafter reuses its experts, which has
    never been measured.

### Scaling method

* Per-miss time c = c_fix + c_bw. Only c_bw scales: c_bw' = c_bw x 13.0 / BW.
  * c_bw = expert bytes / today's reader rate: MXFP4 18.80 MB / 13.0 GB/s = 1.446 ms.
  * Fitted totals:
    * verify: 1.369 ms/miss (D9, 2,171 rounds)
    * plain step inside a DSpark session: 1.490 (D9 probes)
    * plain decode: 1.442 (D4, across cache sizes)
  * These are equal to the transfer time within -5..+3 %, so c_fix is about
    zero.
  * High case: c_fix = 0.
  * Low case:
    * c_fix = 0.15 ms/miss, a bound that is larger than any of the differences above;
    * a per-burst latency of +0.06 ms per layer for each extra drive (IO study:
      0.42 ms burst latency on one drive, 0.54 ms on two);
    * the lower reader rates in the configuration table.
* **Test on measured data:** D1 ran on one drive and on two, with the same
  binary and the same token trajectories (`d1-mx-*-1d-*` vs
  `d1-mx-*-2dc-*`):

  | run | misses/token | measured, 2 drives -> 1 drive | modelled, 1 drive (reader at 94 % .. 89 %) | c_bw implied by the measured change |
  |---|---:|---|---|---:|
  | plain code | 28.39 | 7.99 -> 5.92 | 6.01 .. 5.84 (+1.4 .. -1.4 %) | 1.525 ms |
  | plain prose | 22.43 | 8.68 -> 6.68 | 6.76 .. 6.60 (+1.2 .. -1.2 %) | 1.527 ms |
  | DSpark code (old) | 30.31 | 7.82 -> 5.76 | 5.81 .. 5.65 (+0.9 .. -1.9 %) | 1.498 ms |

  The measured change is as large as, or slightly larger than, pure
  bandwidth predicts. So no hidden fixed part shows up at the lower
  bandwidth. **Support: good for 1 <-> 2 drives; untested above 2.** The D1
  binary predates D2's read/compute overlap. Overlap can only reduce the
  exposed read time, but D9's slope of 1.37 ms/miss on the current binary is
  still close to the transfer time.
* **Everything else is held fixed:** non-read time (verify
  77.2 + 14.2·rows ms; plain decode 77 ms per token from D4), the drafter
  (20.2 ms), acceptance (the D9 probe data) and misses per row (per prompt
  and cache, from the records).
* **DSpark tok/s:** the D9 replay (`sim.py`) runs the old scheduler, the
  model scheduler with its constants refitted per configuration (table
  below), and the oracle.
  * The anchored value is today's measured tok/s × the modelled gain. This
    is used because the replay runs on the plain text, while measured
    DSpark runs drift to their own text (D9).
* **Plain tok/s:** ms/token = measured ms/token − 1.442·m + c'·m, with m
  taken from the `perf token` lines.
  * Checks for today: code 8.45 (measured 8.45), prose 9.12/9.14, json
    8.95/8.95, translate 9.02/9.02, list 9.59/9.59, int2 code 9.11/9.15,
    int2 prose 9.78/9.80.
* Model scheduler constants, refitted per configuration (high case; low case
  in brackets):

  | config | P (plain step) | VA + VB·rows |
  |---|---|---|
  | today | 117.7 | 77.2 + 49.9 |
  | 3 internal | 104.5 [108.9] | 77.2 + 38.1 [40.9] |
  | +1 USB4 | 100.5 [107.7] | 77.2 + 34.6 [38.5] |
  | +2 USB4 | 97.6 [109.2] | 77.2 + 31.9 [38.5] |

  Cheaper rows shift the best width up.

### What could make the real gain lower

* **No third Gen4 x4 port is verified.** Both M.2 slots are used. A third
  drive needs the board's x4 PCIe slot through an adapter (IO study: not
  checked physically). A shared upstream limit above 13.8 GB/s has not been
  tested.
* **Code change:** the replica reader supports exactly two files. Spreading
  reads over 3-5 copies of unequal speed needs a new read scheduler; it
  could reach less than 94 % (the low case assumes 88 %).
  * The "least-loaded" chunk policy with one slower USB4 member could make
    tail latency worse within a layer burst. A layer's reads wait for the
    slowest piece.
* **USB4:** the 3.6 GB/s is a vendor figure, not measured. The enclosure
  bridge, its thermals (enclosures throttle) and the USB4 controller layout
  are all unknown. Two enclosures may share one 40 Gb/s link (the low case
  assumes they do).
* **Thermal throttling:** the system drive already reaches 84-85 C in ds4
  runs and throttles at 89 C. An extra drive in an adapter or enclosure
  needs airflow. Bench cooldowns hide this; sustained use does not.
* **dm-crypt CPU:** about 0.3 core-s/GB with workqueues bypassed (data
  drive) and 1.35 core-s/GB with the default kcryptd (root drive). At about
  20-26 GB/s in bursts, that is 6-10+ cores of decryption competing with
  ds4's host threads, unless every extra volume bypasses the workqueues.
* **Per-burst latency** may grow faster than the +0.06 ms per drive assumed
  in the low case.
* **More bandwidth may not show up at all if** a future change makes decode
  compute-bound (perfect overlap), or makes reads smaller (a bigger cache).
  * The gains here assume today's read structure.
  * The IO study's perfect-overlap bound for DSpark is 20.6 tok/s at two
    drives, rising to ~29 at three.
* **Storage:** each drive must hold a full copy of the model (MXFP4
  501.6 GB, Q2 366 GB).
* **Untested regions:** the scaling was tested from 2 drives down to 1, not
  up. Throughput is extrapolated from 2 measured drives to 3-5.

## Part B: what the drafter's memory holds

Source: the DSpark GGUF header and tensor table only (8,048 bytes read), plus
the main model's tensor table (5.8 MB read), plus the code. Script
`scripts/d10/gguf_table.py`; tables in `out/*_table.json`.

The drafter file is 8.04 GiB in 81 tensors:
* three stages of a V4.1 block with 128 MXFP4 experts each;
* a 3-way main projection of target layers 37-39 (stage 0);
* the Markov head (rank 256) and the confidence head.

**It has no embeddings and no output head.** The drafter uses the main
model's `token_embd` and `output` (`ds41_draft_propose`,
`ds41_output_projection`), so nothing is duplicated there.

**How it is loaded (ROCm):**
* The whole file is chunk-copied once into one device allocation of 8.04 GiB
  ("ROCm chunk-copying 8.04 GiB model image"). The host source pages are
  discarded after the upload (`cuda_model_discard_source_pages`), so no host
  copy is kept. This is from reading the code, not a measurement.
* The SSD expert cache is charged the file size (8.04 GiB, 4,947 → 4,487
  experts).
* Outside that charge sit:
  * the transposed F32 Markov head, 126 MiB, built at start-up;
  * the drafter's own buffers, about 20 MB in total: feature ring 7.5 MiB,
    KV rings, the saved-trunk slots and the 5 × 129k logits.

**Inventory** (from `out/d10b.txt`; "read" is from the code and the D9
drafter profile):

**Byte-compare (under the lock, 0.33 GB read, `out/bytecmp.json`).** The only
large drafter tensors whose shape and type equal a main-model tensor are the
three `mtp.N.attn_kv` (F16 5120×512). Their twins are seven
`blk.{2,8,..}.attn_compressor_kv/gate` tensors. All ten were hashed whole:
**none are equal.**

I also tested whether the drafter's experts are copies of the experts of its
target layers 37-39. I hashed the first 64 KiB of every drafter expert slice
(3 stages × gate/up/down × 128) and of every main-model expert slice of
layers 37-39 (3 × 3 × 384). **0 of 1,152 matched.** The drafter's experts are
its own weights.

## Deviations

* **Q2:** the brief framed Q2 against two drives. Q2 has no replica and reads
  from one drive today. I modelled 1 → 2 → 3+ drives for it, and the extra
  drives need Q2 replicas.
* **USB4 low case:** for two USB4 enclosures it assumes they share one link,
  so it equals one enclosure. That is a choice of pessimism, not a
  measurement.
* **Byte-compare scope:** besides the shape-equal `attn_kv` tensors, it also
  compared 64 KiB prefixes of every expert slice. Total read was 0.33 GB
  under the lock, well under the 10 GiB limit. It ran between int3 runs, and
  the flock waited for the lock to be free.
* **Nothing implemented** in Part B, as asked.

## Not verified

* All Part A tok/s are modelled.
  * The scaling was tested only on the 1 ↔ 2 drive step, with D1's binary
    (no D2 overlap).
  * The third-drive ceiling (20.66 GB/s) is the IO study's extrapolation; the
    USB4 figure is a vendor number.
  * Reader efficiency at 3+ drives does not exist yet (it needs code).
* The anchored DSpark values combine today's measured tok/s with a gain
  modelled on the plain text. Measured DSpark runs drift to other texts with
  other miss rates.
* Plain decode uses 77 ms of fixed time and D4's 1.442 ms/miss. The int2
  plain check fits within 1-2 %. json/translate/list on int2 were not run
  plain, so they are not in the int2 plain rows.
* Part B:
  * "never read" for markov_w2 and the vision biases, and "no host copy", are
    from reading the code; no memory measurement was made.
  * Drafter expert reuse, which decides candidate 1, is unmeasured.
  * The 0.12 tok/s per GiB is extrapolated beyond D4's measured range.
* Cheapest validation before buying anything (not run; needs your go):
  * The 1-drive point is already measured. The next step would be a
    single-drive vs two-drive pair on today's binary (2 runs, ~6 min).
  * Also the drafter router trace above.
