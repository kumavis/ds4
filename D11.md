# D11: drafter expert reuse, and the drive model checked on today's code

Branch `d11-drafter-experts` in `/data/ds4-d11`. It is `kumanix-int2` (249ca97)
merged with `d9-dspark-economics` (3cc75a5) in c508165, plus the trace (8d3dff2).

* Scripts and outputs are in `scripts/d11/`: `out/partA.txt`, `out/reuse.txt`,
  `out/lru_only.txt`.
* Queue logs: `/data/ds4-bench/d11-queue.log` (Part A) and
  `/data/ds4-bench/d11-queue-b.log` (Part B).
* Every tok/s marked "estimate" is modelled; all others are measured
  (`results.jsonl`).

## Bottom line

* **The drive model holds on today's code for plain decode.** It is slightly
  pessimistic for DSpark.
  * Predicted one-drive tok/s on the int2 binary was written down before the
    runs (`scripts/d11/prediction.txt`): plain 6.78-6.96, DSpark (old) 7.68-7.97.
  * Measured: plain 6.815 (6.81, 6.82), inside the range. DSpark 8.105 (8.08,
    8.13), 1.7-5 % above the range.
  * Implied extra cost per miss going from two drives to one: plain
    1.583 ms, DSpark 1.324 ms, against 1.457 ms for pure transfer.
  * With D2's read/compute overlap, plain decode still scales like pure
    bandwidth (9 % above it). DSpark scales at 0.91 of it, because verify
    hides part of each read behind compute.
  * So D10's DSpark gains for extra drives are about 10 % too high in relative
    terms (e.g. +10..+16 % becomes about +9..+14 %; estimate). The plain
    figures stand.
  * No run reached 86 C (max 84 C). All gates passed.
* **The drafter reuses its experts a lot, but not in a fixed set.**
  * Each proposal selects 15 experts per stage (5 positions x top-3) but only
    5-10 distinct ones.
  * Over a 512-token run a stage uses 21-89 of its 128 experts. Across all
    five prompts, stage 0 uses 110, stage 1 82, stage 2 47.
  * A per-stage LRU of 32 slots hits 84-91 % of expert lookups.
  * A static hot set does not generalise. With the top-32 chosen on the other
    four prompts, coverage of the held-out prompt is 0.60 (code) to 0.90
    (prose).
* **Moving the drafter's routed experts out of resident memory is worth only
  about +2..+6 % per prompt (estimate).** Freeing 4-5 GiB buys about
  +0.5-0.65 tok/s at 0.12 tok/s per GiB. Drafter misses then cost 2.9 ms each
  on one drive, which takes back about half of that.
  * Best options:
    * the shared main expert cache: mean +4.0 %, Q2 +1.5 % (estimate);
    * a per-stage LRU of 48: mean +3.1 %, Q2 +1.1 % (estimate);
    * a leave-one-out static hot set of 32 plus an LRU of 16: mean +3.4 % (estimate).
  * Dropping the non-hot experts (1c) would change 1.6-40 % of selections;
    that needs the owner's yes, and it is not worth it.
  * **My recommendation:** build it only after the bigger items on the read
    side. If it is built, use a per-stage LRU of 48 drafter experts
    (deterministic, no static list, frees 4.2 GiB). The gate is that proposals
    are bit-identical (below).

## Part A: drive model against one-drive runs on the int2 binary

Method (D10): the two-drive anchors are `int2-mx-code-plain-r1/r2` (9.13/9.17)
and `int2-mx-code-dsp-r1/r2` (11.83/11.96). Misses are taken from those
records:
* plain: 23.66 per token (`perf token` lines);
* DSpark: 25.57 verify misses and 4.12 plain-step misses per token.

Each miss's time grows by its fitted slope × (scale − 1). Slopes: plain 1.442,
verify 1.369, session plain step 1.490 ms. Scale = 13.0 GB/s / one-drive reader
rate (94 % or 89 % of 6.89). The prediction was written and saved at 15:27 HST,
before the first run started (`scripts/d11/prediction.txt`).

Runs: `DS4_DIR=/data/ds4-int2`, the same environment as the int2 records
(`DS4_D8_STEP_TRACE=1`, and on DSpark `DS4_ROCM_DSPARK_PHASE_TRACE=1
DS4_DSPARK_SCHED_TRACE=1`), with `DS4_ROCM_STREAM_REPLICA` removed.

| tag | tok/s | check | nvme_temp_max_c | avail_min_mb |
|---|---:|---|---:|---:|
| d11-1d-smoke-plain-8 | 6.35 | - | 77 | 13803 |
| d11-1d-plain-r1 | 6.81 | digest 8290541d324b/511 | 79 | 13696 |
| d11-1d-dsp-r1 | 8.08 | 172 rounds / 340 accepted | 79 | 13480 |
| d11-1d-plain-r2 | 6.82 | digest 8290541d324b/511 | 79 | 14070 |
| d11-1d-dsp-r2 | 8.13 | 172 / 340 | 84 | 13250 |

No run reached 86 C, so all four count as validation.

| | predicted, reader 94 % | predicted, reader 89 % | measured | implied extra ms per miss, 2 → 1 drive (pure transfer: 1.457) |
|---|---:|---:|---:|---:|
| plain code | 6.96 (+2.1 %) | 6.78 (−0.5 %) | 6.815 | 1.583 |
| DSpark old code | 7.97 (−1.7 %) | 7.68 (−5.2 %) | 8.105 | 1.324 |

**Does pure bandwidth scaling hold with D2's overlap?**
* **Plain:** yes. The measured slowdown is 9 % larger than pure transfer
  predicts. The same was true on D1's binary without overlap (1.525 ms), so
  the overlap does not hide a measurable part of plain decode's reads.
* **DSpark:** about 0.91 of pure transfer. Verify rows hide some read time
  behind compute, so one drive costs less than predicted.
  * Applied the other way, more drives would gain somewhat less than D10's
    high case.
  * Scaling D10's DSpark gains by 0.91 (estimate): three internal drives give
    about +9..+14 % on the int cache (D10: +10.4..+15.8 %) and about
    +8..+13 % on int2 (D10: +8.9..+13.8 %).
* **Limits:**
  * This tests the step down from two drives to one, not the step up to
    three or more.
  * It covers code only, two runs each.

### Trace (8d3dff2)

`DS4_D11_DRAFT_TRACE=1`, off by default:
* After each drafter stage's router selection, a stream-ordered device copy
  moves the selected ids into a small buffer.
* After the proposal, next to the drafted tokens, the buffer is read and one
  line is printed:
  `D11_DRAFT v=1 pos= seed= block= used= drafts=... s0=e,e,e|e,e,e|... s1=... s2=...`
  (3 ids per drafted position per stage).
* No decision reads it.

### Options against today's all-resident drafter (estimates)

Baseline: the measured tok/s of each trace run, with all 6.72 GiB of drafter
experts resident. Assumptions:
* Freed memory goes to the main expert cache at 0.12 tok/s per GiB (D4's
  slope). The freed 4-5.5 GiB lands int2's 74.7 GiB cache at 79-80 GiB, inside
  D4's measured 47-84 GiB range.
* A drafter miss reads one 18.8 MB expert from the data drive at 2.9 ms, fully
  exposed (the drafter has no overlap).
* tok/s' = 511 / (511 / (tps + 0.12 × freed GiB) + misses × 2.9 ms).

### Recommendation

The gain is small: about +3-4 % on MXFP4 and +1-2 % on Q2 (estimates).
Half of the memory value is spent on one-drive drafter reads. I would build
it only after the read-side work that moves DSpark more (D9/D10: more misses
per row are the main cost).

If built, use **(1b-lru): an LRU of 48 drafter experts per stage**, with the
remaining experts read from the DSpark file on demand.
* It frees 4.2 GiB and keeps a 90-95 % hit rate (89.7 % code, 89.6 % Q2, up to 94.7 % translate).
* It needs no static list, and a static list would not generalise (see
  leave-one-out).
* It is deterministic: its contents depend only on the selection sequence.
* It is self-contained: it does not mix drafter entries into the main cache
  policy.

Option (1), via the main cache, is about 1 point better on paper. But it
makes drafter misses depend on the main cache's traffic, and it needs the
drafter MoE to read from main-cache slots. A further refinement for either
option: issue the reads for all of a stage's missing experts at once, right
after that stage's router selection.

Exactness gate for the build (proposals bit-identical, nothing else may move):
1. Run the five prompts with the option on and off: equal rounds and accepted
   drafts, and equal md5 over every `D9_ROUND` line (pos, width, matched,
   drafts, confidence logits in hex), as in the trace gate above.
2. `--dspark-verify exact` with `DS4_REF_TAG` against plain: 511/511,
   logits bit-exact.
3. Plain digests unchanged (MXFP4 8290541d324b/511, Q2 f0a2cd53a247/511).
4. A forced-cold test: an LRU of 1 slot per stage. Every drafter expert is
   then read from SSD on every use, and the D9_ROUND hash must still match.

## Deviations

* The DSpark miss-count gate ("same misses as int2-mx-code-dsp-r1") cannot
  hold exactly on the int2 binary: int2's own repeats differ by up to 0.25 %.
  I gated on bit-identical proposals instead (a stronger check for this
  trace), plus rounds and accepted. Miss counts are within int2's spread.
* Part A had a smoke run (`-n 8`) on the existing int2 binary before the
  measured runs; it was not required.
* **Extra option:** besides 1, 1b and 1c, I added (1b-lru), a pure
  per-stage LRU, because the leave-one-out results show a static hot set does
  not carry over between prompts.
* **Memory:** avail_min_mb went as low as 12,828 MB (translate trace). It
  stayed above ~12 GB on every run, but the margin on the int2 binary is
  thin. The int2 records themselves sit at 13.4-14.0 GB.

## Not verified

* **Part A:**
  * It checks scaling from two drives down to one. Three or more drives (and
    USB4) remain D10 extrapolations.
  * Code only, two runs each.
* **Option tok/s are estimates:**
  * The 0.12 tok/s per GiB slope is from D4.
  * The fully exposed 2.9 ms per drafter miss assumes no overlap and
    one-drive reads.
  * Option (1) uses the 140-token residence estimate.
  * Not modelled: drafter reads competing with verify reads for the drive.
    They are sequential today, so no conflict is expected.
* **Generalisation:** the reuse statistics come from 512-token runs of five
  prompts. Longer sessions would amortise the cold misses (lower miss rates);
  other domains may use other experts.
* **Miss repeatability:** why int2's miss counts vary from run to run was not
  investigated.
