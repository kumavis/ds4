# D12: expert-cache eviction policy, trace-driven bound

Branch `d12-cache-policy` in `/data/ds4-d12`, from `d11-drafter-experts`
(0d818ed). Trace commit d690aed (build); scripts under `scripts/d12/`; queue log
`/data/ds4-bench/d12-queue.log`; traces `/data/ds4-bench/d12-traces/*.trace.gz`
(not in git, 13 MB). MXFP4, two drives, 512 tokens unless stated, `--nothink` on
code only, DSpark old scheduler. Every tok/s figure marked "modelled" is an
estimate from the D4/D9 cost model, not a measurement.

## Bottom line

* **The bound is large; no realizable policy gets near it.** Belady's optimal
  at the same slot count removes 55-63 % of steady-state misses (tokens
  129-512) on every prompt, plain and DSpark: modelled +13 to +21 % tok/s plain
  and +18 to +35 % DSpark over the whole generated run. Belady at the current
  ~4,740 slots has fewer misses than LRU at 5,300 slots, about 10 GiB more memory.
* **The best realizable policies remove 1-16 % of steady-state misses and
  hurt the warm-up.** S3-FIFO was best: -10 % code, -16 % prose and -1 to -8 %
  on the rest. The decayed-frequency score with a 64-token half-life and an
  online-adaptive version of it come close. Over the whole run the modelled
  gain is +0.1 to +3.7 % (mean about +1.6 %). Tokens 1-128 get up to 13 %
  *more* misses (DSpark prose).
* **Recommendation: nothing clearly worth building.** S3-FIFO passes the
  bar as stated only at the runtime slot count: at least 5 % fewer
  steady-state misses on 9 of 13 traces (6 of 10 prompt/mode pairs), and no
  steady-state loss. It is not robust: warm-up losses up to +13 %; at
  +500 slots, list gets +2 % steady and +17 % warm-up; on prose the gain is
  gone after token 512. Its expected value is about +1-2 % tok/s. If the PM
  wants it anyway, it is a small, deterministic, O(1) change; the spec and gate
  are in section 7.
* **Why the gap:** first use (compulsory) is only 15-53 % of decode misses.
  Belady removes about half of the rest by knowing which experts come back. Recency and
  frequency barely predict that: long-memory popularity (half-life of 512 tokens or more, the
  P3 design) makes things *worse* on most prompts (+3 to +44 %). That
  explains P3's "no measurable gain". The remaining headroom belongs to
  prediction (router-informed eviction or prefetch), not to a better recency
  rule. That is a hypothesis; it is not measured here.
* Gates pass: trace off and on give identical digests (code 8290541d324b/511, prose
  88ed0e11adfd/511, smoke 8 and 64 tokens), and DSpark code gives 172/340 with the trace off and on. The
  simulator reproduces every hit, miss and evicted key of all 13 traces
  exactly.

## 1. The runtime's policy (read from the code)

`rocm/ds4_rocm_runtime.cuh`, `cuda_stream_resident_evict_one`:

* **Global LRU.** One clock `g_stream_resident_clock` is bumped on every lookup hit, every insert,
  the pointer-table upload (`cuda_stream_selected_prepare_ptrs`, all six of a
  step, in slot order) and every compaction copy (`_compact_mask`).
* **Victim choice.** The victim is the entry with the oldest clock that is not in the
  current call's set (same layer, expert among the call's ids). The scan is O(n), about 4,700 entries per eviction.
  `DS4_ROCM_STREAM_EVICT_PAST_LAYERS_FIRST` (off) is the only variant.
* **When eviction happens.** Only when no slab slot is free and the pool is
  at its budget, which is sized from free memory at startup. These runs had
  4,719-4,741 slots plain and 4,253-4,269 with DSpark.
* **Prefill.** Prompts under 256 tokens run token-major: each prompt token
  is an ordinary single-token step through the same cache. Prompts of 256
  tokens or more (json 273, translate 283, long 1,445) use the layer sweep.
  The sweep reads whole layers into the two staging slots. It copies resident hits
  out of the cache without touching the clock (`cuda_stream_v41_prepare_layer`).
  It then seeds the decode cache per layer through
  `ds41_prefill_seed` → `cuda_stream_resident_seed_experts`: up to
  budget/40 experts per layer, with the last 32 prompt tokens dominant. That
  fills the whole cache (4,720 seeds plain, 4,240 DSpark).
* **Staging slots** (`g_stream_layer_expert_cache[2]`) are separate memory,
  not cache slots. Nothing is pinned in the resident cache. The whole cache
  is released only at start and teardown (the `F` lines). There were no flushes in the middle of any run.
* **Verify rounds.** One batched lookup per layer over the union of
  the round's rows, in first-occurrence order. The whole union is protected
  while that layer's misses are allocated.

## 2. Trace switch `DS4_D12_CACHE_TRACE=<file>`

Commit d690aed: +104 lines in `ds4.c`, `ds4_gpu.h` and `rocm/ds4_rocm_runtime.cuh`.
The trace is compact text, fully buffered (8 MiB) and flushed at exit.
In cache order it records:

* `M kind pos rows budget slots resident free`: phase marks from `ds4.c`. `S` is
  `ds41_graph_step`, `V` is `ds41_graph_step_batch` (verify round), `P` is the
  layer-sweep prefill.
* `A src map layer n_tokens n_sel ids…`: one cache call and its protected set.
  `src` is `s` (step), `b` (batched verify), `d` or `e` (seeds).
* `h`/`m layer expert`: a lookup hit or miss. The `x layer expert` lines that follow a miss are the
  evictions it caused.
* `t`: a clock bump without a lookup.
* `F`: a full release.

Off, it costs one cached branch per call site. Sizes are 0.5-1 MB per 512-token run
gzipped, and 3.5 MB for code at 2,048 tokens.

## 3. Simulator and its validation

`scripts/d12/validate.py` replays each trace with the runtime's exact rule:
the clock order including `t` bumps, the victim is the oldest unprotected entry,
and evictions happen where the trace has them. It checks every hit or miss and every
evicted key. **All 13 traces: 0 mismatched hits or misses, 0 wrong victims, 0
stray evictions.** The trace's miss totals equal the harness record's
`decode_misses + prefill_misses` (for example code 17,439+0, DSpark code 7,579+13,055). Prefill
seeds are counted in neither. Evictions always occurred with the
resident count equal to the run's slot count.

`scripts/d12/sim.py` runs the policies over the demand stream, with the
runtime's constraints:

* every looked-up expert must be resident (no bypass);
* the call's protected set cannot be evicted;
* seed calls insert like the runtime but are counted apart (they are device copies, not reads).

Its plain LRU, without the `t` bumps, gives exactly the runtime's misses on
all 13 traces. So the bumps never change a victim, and every number below is
"policy X vs the runtime's LRU" on identical streams.

Notes on specific policies:

* **Belady (MIN):** call granularity. All ids of one call, meaning one layer of a step,
  or the union of a verify round's rows for that layer, are needed at the same
  instant. The next use is the next call that looks the key up.
* **lfu:H:** a decayed count with a half-life of H token positions. History is kept for evicted keys.
* **alfu:** shadow caches (metadata only) for H ∈ {LRU, 16, 64, 256}. Every 32
  tokens the real cache switches to the one with the fewest shadow misses.
* **lru2:** LRU-K with K = 2.
* **arc, 2q, lirs:** the published algorithms. `lirs:0.1` uses 10 % resident HIR.
* **s3fifo:** 10 % small queue, a main queue with a 2-bit count, and a ghost queue.
* **lru-layer-eq / -dem:** per-layer LRU partitions, equal or ½ equal + ½ proportional to
  each layer's LRU misses. The "dem" quotas are fitted on the same trace, so they are optimistic.

Other findings:

* **Half-life.** The half-life matters a lot: on code, lfu goes -5 / -10 / -3 / +9 % for H =
  32 / 64 / 128 / 512 tokens, with a fine scan peaking at 64-72.
* **Per-layer partitions** are worse than global LRU everywhere except the warm-up of the
  layer-sweep prompts.
* **Prefill.** "Protect experts used in the last N tokens from prefill eviction" does not
  apply to these single-turn sessions. A short prompt runs as ordinary steps:
  its 5,316-6,269 prompt misses are 97-100 % first use. A long prompt's
  sweep only seeds an empty cache. The seeds are very valuable: dropping them
  (`lru-noseed`) raises warm-up misses by +39 to +66 % on json, translate and long,
  and leaves the steady state unchanged. The multi-turn case, where a second long prompt
  meets a warm cache, was not traced (single-shot harness).

## 8. Recommendation

**No policy is clearly worth building.** The best candidate is S3-FIFO.

How it measures against the bar:

* At the runtime slot count it has at least 5 % fewer steady-state misses on 9 of 13 traces, and
  no steady-state loss.
* It is not robust:
  * Tokens 1-128 get +5 to +13 % on code and prose.
  * The parameter and slot scan (`scripts/d12/out/s3scan.txt`) shows the gain
    moves with the slot count: list at +500 slots gets +2 % steady and +17 % warm-up.
  * On prose the gain is gone after token 512.
* Its expected value is about +1-2 % tok/s (modelled), similar to adding 2-4 GiB of cache.

If built anyway:

* **Switch.** `DS4_ROCM_STREAM_EVICT=lru|s3fifo` (default lru until A/B'd), in
  `rocm/ds4_rocm_runtime.cuh`.
* **Data structures.**
  * Per resident entry: `uint8_t freq` (0-3), `uint8_t q` (small or main), and
    `uint32_t prev, next`. These link two intrusive FIFOs through the
    `g_stream_resident_experts` vector, so `evict_at` needs an index fix-up
    for the swap-with-last move.
  * Ghost FIFO: a ring of keys of size slots - small (about 4,300 × 8 B) plus a hash set.
    The key is layer × 384 + expert, enough for the single streamed model.
  * Small-queue size: 10 % of slots.
* **Hit** (the three lookup sites in `selected_load`, `batch_selected_prepare_from_host`
  and the seeds): `freq = min(3, freq + 1)`. No list move.
  The `last_used` updates stay for the D5 test hooks and
  `EVICT_PAST_LAYERS_FIRST`; the `t` bumps change nothing under s3fifo.
* **Insert** (`cuda_stream_resident_alloc`): to the main tail if the key is in the
  ghost (remove it from the ghost), otherwise to the small tail. Set freq = 0.
* **Evict** (`cuda_stream_resident_evict_one`):
  * If the small queue holds at least 10 % of slots, pop its head. With freq > 0, move it to the main
    tail with freq 0; otherwise evict it to the ghost.
  * Else pop the main head. With freq > 0, decrement it and move it to the tail; otherwise evict it.
  * Entries in the current call's protected set rotate to the tail unchanged.
  * Each entry is decremented at most three times per insert, so eviction is amortized
    O(1). That is cheaper than today's O(n) scan.
* **Determinism.** It is a pure function of the lookup sequence: no clocks, no timing input.
  It cannot change tokens, since only which bytes are resident changes.
* **Gate.**
  1. Plain digests code 8290541d324b/511 and prose 88ed0e11adfd/511 under both
     settings. DSpark code 172/340.
  2. A run with `DS4_D12_CACHE_TRACE` under s3fifo must match
     `sim.S3FIFO` exactly: every hit, miss and victim. This needs a validator mode
     and is not written yet.
  3. A/B, two runs each, on the five prompts plain and DSpark. Report misses per
     token for tokens 1-128 and 129-512 and tok/s. Accept only if no prompt loses more than 1 %
     tok/s.

**Higher value, not measured.** Belady's 55-63 % says the experts that come
back are predictable in hindsight. A predictor such as D5's early-router probe could
reach part of that by protecting predicted next-layer experts from eviction
or by deprioritising them. That is a separate study (D5's predictor finds 37-40 % of misses).

## 9. Deviations from the brief

* **2,048-token traces.** Prose hit end-of-text at 802 tokens, so its tokens 513-2,048 bucket is
  only 513-802. Code produced 1,976 tokens.
* **Prompt prefill path.** json and translate (273 and 283 tokens) go through the layer sweep with seeding,
  not token-major prefill. Their warm-up therefore starts from a full, seeded cache.
* **Prefill-protection policy.** Not simulated as a policy, because single-turn prefill evicts nothing that decode
  later needs (section 4). I measured the value of the seeding instead.
* **Policies added beyond the brief:** 2Q, LIRS, S3-FIFO, adaptive LFU and more half-lives.
* **Belady counts seeds.** Belady treats seeds as forced inserts, which is what the runtime does. `belady-noseed` is
  in the full tables.
* **Prompt tokens are not in the per-token figures.** In DSpark runs the generated tokens are counted
  by position advance between rounds.

## 10. Not verified

* **No policy was implemented or run on the GPU.** All gains are simulated misses
  converted with the cost model. The miss-to-time model assumes read time scales with
  misses, which D9 fitted with R² 0.995. Prefetch (D5, off here) would interact.
* **Free-running text and one run per prompt.** A different policy cannot change tokens, so the
  streams are exact for these texts. Other texts give other numbers: see
  the spread between prompts.
* **No multi-turn or server traffic**, where a second prompt's prefill meets a warm cache.
* **Q2 not traced.**
* **The plain step inside DSpark** uses the plain cost formula. D9 measured 77.7 + 1.49 × misses
  ms there.
