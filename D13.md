## Bottom line

**What it does.** The switch lends the 768 staging slots to the dynamic expert cache whenever no layer sweep is running. That is 13.45 GiB on MXFP4 and 7.12 GiB on Q2.

**Output.**
- Every plain token-ID digest equals its reference.
- `--dspark-verify exact` is bit-exact against plain decode with the switch on: code and json, 511/511 positions, max logit difference 0.
- DSpark rounds/accepted equal the references on all five prompts and on Q2.
- Two in-process sequences match their switch-off twins token for token. One of them makes a second sweep that hands back 768 populated slots.

**Speed, MXFP4.**
- Plain: +5.8 to +8.1% (two runs each). Code: 9.145 → 9.755 tok/s.
- DSpark: +4.4 to +12.5% (one run each so far).

**Speed, Q2.** No change.

**Memory.** It is already allocated, so MemAvailable does not drop. The lowest reading is 12,855 MiB, at or above 12,288 in every run.

**Recommendation.** Make it the default in the next integration build, after the D5-prefetch gate passes (details at the end).

## What the staging does today (switch off)

From the code, plus fact runs `d13-fact-{code-plain,long-plain,json-dsp}-off` with `DS4_ROCM_STREAM_CACHE_LAYER_STATS=1`.

**Allocation.**
- Allocated once at engine open by `ds4_gpu_stream_expert_cache_reserve_layers`. It is two layer buffers, each holding 384 experts as a gate plane, an up plane and a down plane.
- It is charged in the memory plan as the fixed "prefill staging 13.45 GiB".
- It is freed only at close.

**Who writes it.**
- Only V4.1 layer sweeps write it (`ds41_graph_prefill_sweep` → `ds41_stream_sweep_start`, `cuda_stream_v41_prepare_layer` / `_load_layer`).
- On ROCm, `ds41_prefill_count` sends any remaining prompt under 256 tokens down the token-major path. That path is the single-token decode path, with no sweep.
  - Code (94 tokens), prose (85), hash (55) and list (122) never touch the staging. Their logs show full-layer loads=0: idle for the whole process.
  - json (273), translate (283) and long (1,445) make one sweep each (40 full-layer loads). Prompts of 4,096 tokens or more make one sweep per 2,048-token chunk.

**Plain decode** never reads it. The single-token MoE launch uses the full-layer table only when `n_tokens > 1` or `force_resident`, and V4.1 decode passes `force_resident = !streaming`.

**What it holds after a sweep.**
- All 384 experts of layers 38 and 39, and both layers stay "active".
- In ROCm builds the prefill seed (`ds41_prefill_seed`) has already copied the top `budget/40` experts of every layer (about 118 plain, 106 DSpark) into the dynamic cache.
- Nothing else from the staging is kept. The full layers 38/39 are simply left in place.

**DSpark fast verify (multi-row) does read it after a sweep.**
- Layers 38 and 39 take the full-layer path from the staging. In d13-fact-json-dsp-off, layers 38/39 show batch calls=0 while every other layer shows 141.
- The single-row hit rate on those two layers is only 72–73%, against 92% on the others, because verify never puts their experts into the cache.
- After a short (token-major) prompt nothing reads the staging.

**Keep the staged layers as cache entries instead?**
- Plain long, switch off: decode misses on layers 38+39 were 327 of 6,284, about 1.3 per token.
- So keeping them could save at most ~1.6% (estimate), and would fill 768 slots with only two layers. Not built.

## Design

All of it is in `rocm/ds4_rocm_runtime.cuh` (`cuda_stream_staging_lend`, `cuda_stream_staging_reclaim`), with entry points in `rocm/ds4_rocm_current_api_compat.cuh` and `ds4_gpu.h`, and calls in `ds4.c`.

**Lend.**
- A staging buffer's capacity is exactly 384 × (2·gate + down) bytes, the size of 384 dynamic slots.
- Lending reinterprets each buffer as 384 slot-shaped buffers and pushes them onto the free-slot list. It raises the budget and the slot count by 768 and marks both staging layers inactive.
- From then on they are ordinary slots, filled only by ordinary miss reads. Nothing that was in the staging is turned into an entry.
- Called at engine open (after the reserve) and at the end of every sweep (`ds41_stream_sweep_finish`, after quiesce).

**Reclaim.**
- Called at the start of every sweep (`ds41_stream_sweep_start`, after quiesce) and before the staging is freed at close.
- Steps:
  1. Evict every entry stored in staging memory.
  2. If D5 prefetch is on: drop the shelf's speculative work (as `cuda_d5_shelf_reset` does). Give each shelf entry that holds a staging buffer, after an adoption swap, a non-staging free buffer instead, evicting one LRU entry if none is free.
  3. Remove the 768 staging buffers from the free list. Restore the budget and the slot count.
- If any lent buffer cannot be found, it aborts, matching the existing "refusing teardown" checks.
- The sweep then uses the staging exactly as before. Its D2D reuse of cached experts copies only from slab entries, since the staging entries were evicted.

**Guards.**
- While lent, the reserve, the V4.1 prepare and the legacy full-layer load refuse to run, so the staging cannot be written while slots live in it.
- A full release of the resident cache clears the lent state.
- `ds4_gpu_set_streaming_expert_cache_budget` keeps the lent slots on top of the budget.

**Memory plan.**
- No admission arithmetic changed. It is the same allocation, and `cuda_stream_expert_cache_get_memory` still counts it as layer memory.
- So the D4 plan and the int3 fixed-charge change are untouched.

**Switch off.**
- `ds4_gpu_stream_expert_cache_staging_lent()` is always 0 and no lend is ever called. Behaviour, slot counts and plan are as before.
- Fact runs, switch off: budget 4736 / 4731 / 4271, the same as int2.

**What changes with it on.**
- Cache budget plus 768, all of it filled during decode (peak resident 5,489–5,508 plain, 5,030–5,043 DSpark).
- After a sweep, DSpark verify on layers 38/39 uses the per-slot pointer kernels instead of the full-layer kernels. Rounds and accepted drafts did not change on json or translate, the two sweep prompts.
- Exact verify does not read the staging at all.

### Against D4's slope

768 slots is 13.45 GiB of dynamic cache, beyond the top of D4's measured range (4,780 plain, 4,280 DSpark).

| line | D4 linear fit predicts | log / power fits through D4's end points | measured |
|---|---|---|---|
| plain code misses/tok | −7.3 | −5.7 / −4.1 | −4.84 |
| plain code ms/token | −10.4 ms | — | −6.8 ms (109.35 → 102.51) |
| plain tok/s | +0.75 (+0.056/GiB × 13.45) | — | +0.61 code; +0.54 to +0.80 across prompts (two-run means) |
| DSpark code ms/token | −14.0 ms | — | −9.4 ms (84.4 → 75.0) |
| DSpark tok/s per GiB | +0.125 | — | +0.11 code, +0.03 to +0.07 on the other prompts |

- The gain is about two thirds of D4's linear slope. It lies between the log and power extrapolations (the D4 note said the linear one was the high case).
- The miss saved is still worth ~1.4 ms: plain code 6.84 ms / 4.84 misses = 1.41 ms.
- The brief's guesses were +5–9% plain and +8–13% DSpark (estimates). Measured: plain +5.8–8.1%; DSpark +4.4–12.5%, so only code reached the guessed range.
- Prose, translate and json gain least. On json and translate, layers 38/39 used to be free for verify (full-layer path) and now miss like the other layers. The single-row misses fell more than the batch misses rose; net 22.48 → 19.34 per token on json.

## Interactions

- **D4 memory plan:** unchanged; nothing new to charge. If a later build drops the staging from the plan (for example by trimming it), D13's gain goes with it.
- **D5 prefetch buffer (int3):**
  - The shelf is a separate allocation and stays separate.
  - The only coupling is the adoption swap, which can move a lent staging buffer into the shelf; the reclaim handles it.
  - Queue D ran it with prefetch on: tokens identical and reclaim correct (the shelf-holds-staging branch is not proven to have run).
- **Long prompts:**
  - Each 2,048-token chunk is one sweep, so a long prompt makes several reclaim/lend pairs. Between chunks of one prompt nothing fills the lent slots, so those reclaims evict nothing (the first reclaim in every log: evicted 0).
  - A reclaim after decode evicts up to 768 entries. That is free (no I/O) but drops their contents, so a long agent session loses up to 768 cached experts on every new prompt of 256 tokens or more. Before D13 those slots did not exist, so it is never worse than switch-off.
- **DSpark drafter:**
  - Not involved: its experts are resident in its own memory, and its model map never matches the staging.
  - The drafter's fixed charge in the plan is unchanged.
- **Agent sessions:**
  - Every turn whose new text is 256 tokens or more makes a sweep, which reclaims and then re-lends. Shorter turns keep the lent slots warm.
  - Server mode was not run. The REPL sequence is the closest gate.

## Recommendation

Turn it on by default in the next integration build. Queue D (D5 prefetch on, plus the reclaim) passed:

- no memory cost and no change to the memory plan;
- token-identical on every plain gate and bit-exact under exact verify;
- DSpark rounds/accepted unchanged on all prompts, including the two sweep prompts where the layer 38/39 verify path changed;
- plain +5.8–8.1% (two runs each); DSpark +4.4–12.5% on MXFP4 (one run each, the same direction on all five);
- nothing for Q2.
- also correct with D5 prefetch on.

Worth adding to the integration gates: one D5-on sequence that logs whether the reclaim swapped a shelf buffer. That would turn the "not proven" above into a direct check.

## Not verified

- DSpark gains are single runs (repeat 2 cut by decision).
- That the D5 shelf hand-back branch of the reclaim actually executed (see the D5 gate).
- Prefetch alone (switch off, prefetch on) for plain code on this binary, so the D5 increment over staging alone (9.755 → 9.90) is not separated cleanly.
- Server mode and multiple sessions (session hint > 1); contexts above 4,096; `encoder_only` / deferred-decoder sweeps (prompts of 16k tokens or more); TP; the GLM path. The switch is V4.1 ROCm only.
- The abort in the reclaim, if a lent buffer goes missing, is a should-not-happen check. It never fired.
