# D14: agent-session benchmark, first baseline

Branch `d14-agent-bench` (from `d11-drafter-experts` 0d818ed), worktree
`/data/ds4-d14`. Scripts are in `scripts/d14/`. The server under test is
`kumanix-int2` (`/data/ds4-int2/ds4-server`, 249ca97, built from 28dfbb7),
unmodified. Setup: MXFP4 with the replica on the second drive (two-drive
reads), `--ssd-streaming`, greedy (`temperature 0`), non-thinking
(`think: false`). Records are in `/data/ds4-bench/sessions.jsonl` (one row
per turn and one per scenario); logs are in `/data/ds4-bench/runs/*-d14-*`.
Estimates are marked as such.

## Bottom line

One coding-agent session on this box today (MXFP4, two drives, payload v2,
`--ctx 163840`, the live session reused between turns). Medians per context
fill; "new" is the median number of new prompt tokens per turn (tool output
plus instruction).

| Fill | Turns | New tok | TTFT, plain | TTFT, DSpark | Prefill, new tok/s | Decode tok/s, plain | Decode tok/s, DSpark | Misses/tok, plain (first 16 / rest) | MemAvailable min, plain / DSpark |
|---|---|---|---|---|---|---|---|---|---|
| ~16k (12-21k) | 5 | 2,581 | 56 s | 60 s | 46 | 8.42 | 9.16 | 62 / 27 | 13,296 / 12,955 MiB |
| ~32k (25-44k) | 7 | 3,983 | 79 s | 81 s | 50 | 8.03 | 8.53 | 62 / 29 | 13,288 / 12,933 MiB |
| ~64k (52-80k) | 18 | 1,192 | 31 s | 33 s | 40 | 7.78 | 9.46 | 55 / 31 | 13,208 / 12,844 MiB |
| ~100k (81-114k) | 18 / 9 | 1,437 / 1,911 | 39 s | 50 s | 37 | 7.45 | 10.26 | 56 / 33 | 13,387 / 12,660 MiB |
| ~128k (119-132k) | 8 | 1,294 | 38 s | not reached | 35 | 7.24 | - | 57 / 36 | 13,387 MiB |

- **Plain** reached 132,325 tokens in two server sessions: 0 to 66k, then
  restored from disk after a restart and grown on.
- **DSpark** was stopped by the memory guard at 98.6k: before a turn,
  MemAvailable was within 512 MiB of the 12,288 MiB floor. The minimum
  sampled was 12,660 MiB, so the floor was never crossed, but there is no
  DSpark figure at 128k.
- **DSpark gain.** DSpark (`fast` verify, `DS4_DSPARK_SCHED=old`) gives
  +6% to +38% over plain decode at the same fill. It accepts 1.55-3.34
  drafts per round and the scheduler skips drafting on about half the
  steps, so agent text is a weaker case for DSpark than the single prompts
  (9.7-12.7 tok/s).
- **First turn, cold system prompt.** 7.5k tokens of system prompt plus the
  first message take 131-158 s to the first token.

**The four largest costs for this load, each measured:**

1. **Prefilling each turn's new tokens: 64% of the plain session's time**
   (54 min prefill against 31 min decode, over 0 to 132k).
   - Every prefill chunk of up to 2,048 tokens reads the whole routed-expert
     set from the drives: about 220 GiB per chunk, 560 full-layer loads and
     3,765 GiB for one 29k session.
   - So a 256-token tool result costs ~20 s, a 1.2k-token one ~33 s and a
     4k-token one ~70-110 s (37-50 tok/s). Only prompts of a few tokens
     (<= ~40) go the cheap token-by-token way (5-6 s).
   - A long one-shot prefill uses 32,768-token chunks and runs at 96-122
     tok/s.
   - `--prefill-chunk` is ignored on V4.1 ROCm. The fork's one-sweep path
     for 2-8k appends exists for CUDA but is compiled out for ROCm (see
     the techniques section).
2. **Decode gets slower with context, mostly through expert misses.**
   - Plain decode goes from 8.42 tok/s at ~16k to 7.24 at ~128k: the step
     is +19 ms (119 to 138 ms).
   - Misses per token after the first 16 reply tokens rise from 26.5 to
     35.7. At the measured ~1.44 ms per miss that is ~13 ms of the 19 ms
     (estimate); the rest (~6 ms) is attention and the indexer at longer
     context (estimate).
   - In addition, the first 16 reply tokens after every prefill miss 55-62
     experts per token instead of 27-36, because the prefill evicts the
     decode working set. That costs about 16 × 28 × 1.44 ms ≈ 0.65 s per turn
     (estimate): real, but small next to cost 1.
3. **Restoring a session after a restart: TTFT 368 s at ~101k, against
   911 s cold; it could be about 40 s (estimate).** The disk KV cache restored only an
   old checkpoint every time, for two reasons:
   - **Few checkpoints.** A "continued" checkpoint is written only when the
     live position equals an exact multiple of 10,240 tokens. Agent turns
     are mostly prefilled tool output that jumps over the frontiers, so the
     132k session saved 3 continued checkpoints (20k, 31k, 61k) plus the
     shutdown saves.
   - **Text key mismatch.** Checkpoints are keyed by the decoded token
     text, and ds4's chat tokenizer turns ASCII spellings such as
     `<|user|>` and `[gMASK]` inside tool output into special tokens. A
     client that resends its history verbatim then misses every checkpoint
     after the first such string: the plain session fell back from 66k to
     30,720 tokens (TTFT 388 s at 68k).

   With the history rewritten token-identically, a restore at 64k hit the
   full 66k checkpoint (434 MB, 32 ms) and the turn's TTFT was 62 s. The
   checkpoints are small: ~6.3 MiB per 1k tokens, 819 MiB at 132k, saved in
   0.3-0.5 s.
4. **Several sessions: no prefix sharing, and concurrent prefill collapses.**
   - With `--batched-session 2`, each session prefilled the shared 7.4k
     system prompt itself.
   - While one session was prefilling, the server ran that prefill token by
     token (~10 tok/s instead of ~55) and the other session decoded at
     0.19 tok/s. TTFT of session 1's first turn: 1,049 s (10.3k tokens),
     against ~150 s alone.
   - On ROCm the batched decode is a serial loop over sessions (code and
     docs agree) and DSpark is disabled in batched mode.

## Payload and driver

All scripts are in `scripts/d14/`. The ds4 code is unchanged.

**Payload: `gen_payload.py`.** Seeded and stdlib-only, no network, no
private data. Every byte is either written in the script or taken from the
public ds4 source files in this worktree (commit 0d818ed; the benchmark's own
files are excluded). The same seed and tree give byte-identical output
(checked: same sha256 twice).

- **System prompt** (shared by all sessions): agent instructions written for
  this benchmark, 20 JSON tool schemas (read_file, write_file, edit_file,
  apply_patch, grep, glob, list_dir, run_command, build, run_tests,
  run_benchmark, git_status/diff/log/commit, symbol_search, read_log, todo,
  ask_user, web_docs) and a repository file listing.
  - It is 7,375 real tokens in payload v2 (`/data/ds4-bench/d14-payload-v2.json`,
    sha256 6a55a1f3280c, `--system-tokens 8100`).
  - Payload v1 (5.5k tokens, e3a58c2c6296) was used only by the first S1 run
    and the stop proof.
- **A turn** is one user-side message followed by the model's reply. The
  message is one of:
  - a user instruction (10%: 50-200 tokens, naming real functions and
    files);
  - an instruction plus one tool result (15%);
  - 1-3 tool results (75%), each wrapped as
    `<tool_result name=... call_id=... arguments=...>`.

  Tool results, by weight: read_file windows with line numbers, 500-4,000
  tokens (42%); diffs from seeded edits of real code (16%); grep over the
  tree (14%); build logs (10%); test runs (8%); directory listings (6%); git
  log (4%).
- **Size and caps.** About 1.9k tokens per turn on average (median 1.4k,
  up to ~8.8k). Reply caps: 256 tokens (70% of turns), 64 (15%), 512 (15%).
- **Sessions.** Four sessions (seeds 14000-14003) share the system prompt
  and diverge after it; each has events for more than 200k tokens.
- **Token counting.** The generator only estimates (chars/3.1 for code,
  chars/4 for prose); real counts are ~0.82-0.94 of the estimate. Every
  recorded count is the server's: `usage.prompt_tokens`,
  `prompt_tokens_details.cached_tokens` (reused) and `completion_tokens`.

**Driver: `driver.py run`.**

- Requests are OpenAI `/v1/chat/completions`, streamed, with
  `include_usage`, `temperature 0` and `think: false`, one connection per
  request.
- The model's own streamed reply is appended to the history as the
  assistant message and sent back on the next turn. That includes the DSML
  tool-call text the model emits; the server's exact-replay map keeps it
  reusable.
- Steps:
  - `grow`: one session to a target fill, optionally continuing a saved
    transcript after a restart;
  - `resume`: replay a transcript up to the turn nearest N tokens, and
    `salt=1` for a cold control;
  - `multi`: N concurrent sessions;
  - `ping`.
- Guards, checked before every turn: MemAvailable at least 12,288 + 512 MiB,
  a time budget per server session, and the target fill.
- At the end of every scenario the driver performs the clean stop below.

**Per turn it records** (`sessions.jsonl`, `kind: "turn"`):
- prompt, reused and new tokens; TTFT; prefill time and tok/s on the new
  tokens (server log); reply tokens; decode tok/s (all tokens, and after
  token 16);
- KV events with tokens, MiB and ms (live miss, disk hit with load ms, store
  with save ms);
- expert misses per token, first 16 tokens against the rest, read wait and
  slots per token (`DS4_D8_STEP_TRACE=1`, plain and serial-batched decode);
- a drive-read miss estimate (NVMe bytes between reply tokens / 17.93 MiB),
  within 1% of `D8_STEP` on plain turns;
- DSpark rounds, drafted and accepted (`DS4_DSPARK_SPEC_LOG=1`);
- MemAvailable minimum, hottest NVMe and GPU busy from a 2 s sampler (as
  `bench.sh` does);
- reply digests over the text and, for plain decode, over the token IDs.

**Per scenario** (`kind: "scenario"`): the provenance fields `bench.sh`
records (timestamp, tag, model, ds4 commit and dirty flag, every
DS4_*/HSA_* variable, server flags, run directory, exit status), the memory
plan, whole-life cache and read statistics, the stop details and a digest
of all replies.

Logs are in `/data/ds4-bench/runs/<UTC>-<tag>/`. `table.py` prints every
table below (`turns`, `buckets`, `scenarios`, `resume`); `fit.py` the
prefill bins; `merge.py` the plain/DSpark series.

## How ds4-server is stopped cleanly

From `ds4_server.c` on `kumanix-int2` (249ca97; the binaries were built from
28dfbb7, and the commits after it change only docs and scripts):

- **Signal handler** (`stop_signal_handler`, lines 56-66). The first SIGTERM
  or SIGINT sets `g_stop_requested` and closes the listening socket.
  **A second signal calls `_exit(130)`**, abandoning GPU work. So: exactly one
  signal.
- **Drain** (`main`, 16280-16340). The accept loop ends and the server logs
  "shutdown requested, draining requests". The worker finishes the job it
  holds; `dequeue` returns NULL only when the queue is empty. In batched mode
  every slot thread is joined, then the decode coordinator. Then `main` waits
  for all client threads.
- **No mid-call abort.** Generation checks the flag between tokens. A call
  already in the backend is waited for, not aborted (`server_eval_tokens`).
- **Shutdown save.** With `--kv-disk-dir`, every slot with at least
  `--kv-cache-min-tokens` tokens is saved to disk ("persisting resident KV
  cache before shutdown"). Then the engine closes and the stream-cache /
  read-profile statistics are printed.
- **Connections.** One request per HTTP connection (`Connection: close`), so
  an idle server has no client threads.

**Procedure** (`driver.py stop`, run at the end of every scenario):
1. Wait until the server is idle: no TCP connection on its port, the server
   log unchanged for 5 s, and GPU busy below 25% in three samples in a row.
2. Check that the recorded PID (the launcher shell `exec`s into the binary)
   has `comm` = `ds4-server`.
3. Send one SIGTERM and wait for the process to exit. No second signal, no
   timeout, no SIGKILL. The units are created with `SendSIGKILL=no` and
   `TimeoutStopSec=infinity`; `systemctl stop` is never used on a server.
4. The server holds `gpu.lock` through the inherited fd 9, so the lock is
   released when it exits.

**Evidence.**
- `d14-stopproof` (two 8-token requests, then the stop): "shutdown requested,
  draining requests", cleanup statistics printed, exit 0.2 s after the
  SIGTERM, `EXIT=0`.
- `d14-smoke-after-stop` (`bench.sh -n 8`, record in `results.jsonl`) then
  ran normally (exit 0).
- Every one of the 20+ server sessions since ended the same way: exit in
  0.2-1.2 s, `EXIT=0`. The `stop` field of each scenario record holds the
  idle wait, the SIGTERM time and the exit wait.
- With disk KV on, the shutdown save of a 132k-token session took 328 ms.

## Rerunning on another build

The harness takes the server from `DS4_DIR` (default `/data/ds4-int2`); ds4
itself is not modified. To repeat the main scenarios on another build, with
a new tag prefix so the records do not mix:

```sh
ssh kumanix
cd /data/ds4-bench
# one scenario (S1 to 32k, plain, MXFP4, two drives):
DS4_DIR=/data/ds4-OTHER DS4_ROCM_STREAM_REPLICA=/home/xyz/ds4-replica/DeepSeek-V4.1-Flash-1017-MXFP4-experts.gguf \
D14_PAYLOAD=/data/ds4-bench/d14-payload-v2.json D14_BUDGET_MIN=40 \
DS4_NOTE="D14 rerun on OTHER" \
  /data/ds4-d14/scripts/d14/run.sh d14-other-s1-plain-32k s1 32768 "" grow:target=32768:label=grow
# the long sessions, restores, shared prefix and Q2, in order (about 6 h on the lock):
#   edit the tags in a copy of q_long.sh (d14-* -> d14-other-*), then
systemd-run --user --collect -p SendSIGKILL=no -p TimeoutStopSec=infinity \
  -E DS4_DIR=/data/ds4-OTHER -E D14_CTXL=163840 --unit=d14-q-other /path/to/copy-of-q_long.sh
#   (systemd-run does not pass the caller's environment: use -E; run.sh itself
#    forwards DS4_*/HSA_*/D14_* when it relaunches as a unit)
# tables:
nix-shell /data/ds4-env/shell.nix --run "python3 /data/ds4-d14/scripts/d14/table.py buckets TAG..."
```

`D14_PAYLOAD` must stay `d14-payload-v2.json`, or be regenerated with
`gen_payload.py --src /data/ds4-d14 --sessions 4 --system-tokens 8100`
(same sha256 6a55a1f3280c if the tree is at 0d818ed), so the turns are the
same. Plain decode is greedy and deterministic for an unchanged build: the
same tag twice gives the same `replies_digest` (checked on the six S4 probes,
which share the first two turns). DSpark uses `fast` verify, so its replies
drift by design.

What S2 shows:
- **A restore is only as good as the newest checkpoint below the request.**
  The load itself is cheap (34-254 ms for 20k-66k tokens). With a
  checkpoint at the last turn boundary, a restore at ~100k would cost about
  0.3 s plus the new tokens' prefill: ~35-45 s TTFT, against 368 s measured
  and 911 s cold (estimate, from the 62 s measured at 64k).
- **Defaults do not cover a 100k agent session.**
  - `--kv-cache-cold-max-tokens 30000` only matters for the first prompt
    (7.4k here), so it is not the limit.
  - `--kv-cache-continued-interval-tokens 10000` (rounded to 10,240) is the
    limit: a continued save fires only when the live position equals an
    exact multiple of 10,240 (`ds4_kvstore_continued_store_target`). It is
    checked after a prefill and at each decode step, so in practice only
    when a frontier falls inside a generated reply. The 132k session got
    continued saves at 20,480, 30,720 and 61,440 and nothing between 66k and
    132k. A smaller interval only makes frontiers denser; the rule still
    skips most of them.
  - A setting alone does not fix it. It needs a code change: save at each
    turn end, or split the prefill at the frontier as the cold save does.
- **Special tokens break the text key.** ds4's chat tokenizer
  (`special_token_at` in `ds4.c`) maps ASCII spellings to special tokens even
  inside user and tool text: `<|user|>` and `<|assistant|>` to the V4.1 role
  tokens, `[gMASK]` to BOS, also `<think>`, `<tool_call>` and others.
  Checkpoints are keyed by the decoded token text (`<｜User｜>`), so a client
  that resends the history verbatim misses every checkpoint after the first
  such string. Our payload has one, in a ds4 tokenizer source file at ~44k
  tokens, so the plain session restored only 30,720 of 66k tokens.
  - The driver now rewrites those spellings to the canonical form when it
    rebuilds history (`norm: true`). The tokens are identical, so the model
    input is unchanged, and the full checkpoint then hits.
  - The same mapping means tool output can inject role markers into the
    prompt. That is a ds4 issue worth reporting upstream; nothing is changed
    here.
- **Replies do not continue identically after a restart.** Neither the
  restore nor the cold control repeats the original reply beyond a few to a
  few hundred tokens. Both differ from the original and from each other, so
  the cause is the prefill shape (different chunk boundaries over the same
  tokens give different floating-point order), not the disk restore itself.
  Live reuse within one server session is deterministic: six S4 probes at
  different `--ctx` gave the same reply digest.

  `cached_tokens` 0). Slots do not share prefixes, and no disk KV was
  configured.
- **Concurrent prefill collapses and starves decode.** While one session
  prefills, the server runs that prefill in 128-token quanta
  (`--mixed-prefill-quantum`, default 128) on the per-token expert path:
  ~10 tok/s instead of ~55, and only 200 full-layer loads in the whole run.
  The other session decodes between quanta at 0.2-0.5 tok/s.
  - Two sessions took 42 min of server time to reach 14.8k and 16.5k of
    context.
  - One session alone reaches 17.7k in 7.75 min, so the two run one after
    the other would take ~16 min (estimate). Aggregate throughput is
    therefore below serial, not above.
  - Code and docs agree that batched decode on ROCm V4.1 is a serial loop
    (`ds4_sessions_eval_batch` falls through to `ds4_session_eval` per
    session; SERVER.md "Ordered fallback"). Speculative decoding is disabled
    in batched mode (`!s->batched_mode` gate; the log says "MTP speculative
    decoding is disabled while native session batching is active"), so
    DSpark is unavailable there.
- **Four sessions: not run** (policy, lock time); see deviations. The
  memory plan for 2, 4 and 8 sessions is in S4.
- **Memory per resident session** (from the S4 plans at `--ctx 131072`):
  each extra 128k session adds 3.64 GiB of context buffers and costs about
  210 expert-cache slots.

## What the server does not expose (that we would need)

- **Per-request expert-cache counters.** Hits and misses, full-layer loads
  and bytes read per request: the server prints them only once, at process
  exit (`stream cache stats cleanup`, `stream read profile`). Per decode
  step they exist only through the debug trace `DS4_D8_STEP_TRACE=1`, which
  covers plain decode and the serial batched path but not DSpark rounds.
  DSpark per-turn misses here are a drive-read estimate.
- **DSpark per request.** Totals come only at session free (shutdown); the
  per-round lines (`DS4_DSPARK_SPEC_LOG`) give drafted and accepted, but no
  timings or misses.
- **Prefill cost split.** Chunk count, chunk size, full-layer loads, read
  wait and compute per prefill are not exposed; the prefill log has only
  tokens and elapsed time. The prefill path chosen (full-layer, selected
  experts, per-token) is not logged either.
- **Disk KV decisions.** Why a continued checkpoint was or was not written,
  why a longer checkpoint was not used for a request (text-key mismatch),
  and the restore time split into file read and GPU upload (`load=` ms is
  one figure).
- **Memory at run time.** The server's own view of MemAvailable and of the
  memory per resident session after start.
- **Per-session attribution in batched mode.** Log lines carry a `ctx=` span
  but no slot ID, and `D8_STEP` lines carry neither.

Each of these could be a small statistics patch in a later task; no ds4
code was changed here.

## Known techniques for each cost

The fork's own options come first, then the published recipe
(`ds4/PERF-PLAN.md` section 4).

1. **Prefill of new turn tokens** (64% of session time; ~220 GiB of
   expert reads per <=2,048-token chunk).
   - Fork option `--prefill-chunk N`: **ignored on this path.** The V4.1
     ROCm prefill cap comes from the context size only
     (`ds41_prefill_limit`). With `--prefill-chunk 4096` the server still
     reported `prefill_chunk=2048`, and the TTFT was identical
     (`d14-s1-mx-plain-32k-pc4096`); the 8192 run was skipped by policy.
   - The real lever is code, already in the fork for CUDA. The "medium SSD
     append in one layer sweep" (`ds41` prefill scheduler: appends of
     2-8k tokens in one sweep, "without changing its 2048-row arithmetic
     partitions") is compiled out for ROCm (`!defined(DS4_ROCM_BUILD)`).
     Appends of 4k and more use the wide path in multiples of 2,048 plus a
     tail.
     - Enabling it on ROCm would make every 2-8k turn one expert pass
       instead of 2-4: about 30-45 s saved per such turn at ~20 s per pass
       (estimate). Such turns are 40% of the plain session's turns and most
       of its prefill time.
     - The comment says the arithmetic partitions are unchanged; that needs
       checking on ROCm.
   - Per-token or selected-expert prefill for suffixes of 64-512 tokens: a
     ~20 s full pass for a 256-token tool result is the worst ratio in the
     session. That is a code change.
   - Recipe: faster prefill kernels (hipBLASLt BF16 GEMMs, 4-lane cohort,
     +46%, +25% at 32k) attack compute. Here the chunk cost is dominated by
     reading the experts (~7.5 GiB/s during prefill), so larger chunks and
     fewer passes come first. A third drive (HW-3) would raise the prefill
     read rate, which matters here as much as for decode (estimate).
2. **Decode slowing with context; evictions by prefill.**
   - Recipe: prompt-tail expert retention through prefill (+4.7%) and
     decode hot-set pinning. In D12's scope these address the first-16-token
     miss bump (~0.65 s per turn, estimate) and part of the rise in misses
     with context.
   - Recipe: long-context attention and index work (+5-7%; +16% at 560k)
     addresses the ~6 ms per step not explained by misses at 128k
     (estimate).
   - D13 (staging slots as decode cache) adds cache capacity, which helps
     every fill.
3. **Restore after a restart.**
   - Recipe: disk KV cache with live-session reuse. Live reuse already works
     perfectly (every turn reused the whole previous context).
   - Disk restore needs (a) a checkpoint at each turn end, or a prefill split
     at the continued frontier, and (b) a token-based or
     canonical-text-normalized key, so that special-token spellings in tool
     output do not break the match. Both are code changes; the cost per
     checkpoint is small (~6 MiB per 1k tokens, <0.5 s).
4. **Several sessions.**
   - Fork option `--mixed-prefill-quantum N` (default 128): try 2048 or
     larger, so a prefill is not run token by token beside a decoding
     session. Not measured here.
   - Recipe: session slots with prefill sharing. Today a shared system
     prompt is prefilled per session. A shared-prefix slot copy, or a disk
     checkpoint of the system prompt (it would be a cold save, if
     `--kv-disk-dir` is set), would remove that. Also, the sizer charges the
     full per-session prefill workspace although the server prints a shared
     figure (9.17 GiB against 29.10 GiB for 8 sessions).
   - On this backend batched decode is serial, so more sessions never add
     throughput; with one GPU, the useful mode is one active session at a
     time with fast restore.

## Deviations from the brief

- **S1 and S2 were run as one session.** The long sessions ran with
  `--kv-disk-dir` on from the start, so they also give the save costs. The
  only turn affected is the first: the cold save splits its prefill (+18 s
  TTFT, different reply). The no-disk S1 is `d14-s1-mx-plain-32k` (v1
  payload) and the S4 probes.
- **The long sessions were split across server sessions.** They ran 0 to
  64k, then a restart restoring from disk, then 64k on, to stay inside the
  ~90 min bound. The plain restore at 64k used the verbatim history and fell
  back to the 30,720 checkpoint; it re-prefilled 37k tokens.
- **History normalization.** For the DSpark continuation and the S2
  restores, the driver rewrote special-token spellings in the replayed
  history (token-identical). Without it, the disk cache cannot restore past
  ~44k in this payload.
- **DSpark stopped at 98.6k.** The memory guard (floor + 512 MiB) fired;
  there is no DSpark number at ~128k.
- **The 4-session S3 runtime step was skipped by policy** (lock time; flag
  file `/data/ds4-bench/d14-skip-multi4`). The 2-session run showed the
  mechanism. Four sessions' first turns would have held the lock for an
  estimated 70-80 min. Its memory plan was measured (S4).
- **Payload v1 and v2.** The first S1 run used a 5.5k-token system prompt
  (v1), below the 6-8k asked for. Every later run uses v2 (7.4k).
- **Tool results are scripted, not answers to the model's calls.** The model
  sometimes notices ("the tool results don't match what I asked for"). The
  load shape is right; the reply content is not a quality signal. The model
  also emits DSML tool calls although no `tools` field is sent; the driver
  returns that text as the assistant content, and the server reuses it
  exactly.
- **Reply digest.** Text sha256 (`reply_sha`) for all turns; token-ID digest
  (`reply_tok_sha`) for plain decode only.
- **DSpark parser.** DSpark per-turn fields for `d14-s1-mx-dspark-long-a`
  came from a re-parse after a parser fix (`reparsed.jsonl` in its run
  directory). `sessions.jsonl` was not rewritten (append-only); its rows for
  that tag have null DSpark fields.
- **Context-size probes.** S4 measured decode at 7.5k-12k fill for each
  `--ctx`, not at "the corresponding fill". The fill-dependent numbers are in
  S1, and S4 shows `--ctx` itself does not matter.
- **`--prefill-chunk` was not in the brief.** One run was added, because
  prefill is the largest cost and it is the fork's own option. It turned out
  to be ignored by V4.1 ROCm, so the queued 8192 run was skipped by policy
  (flag file `/data/ds4-bench/d14-skip-pc8192`).

## Not verified

- Whether a disk restore is bit-exact against the same live state. The
  restored and cold replies both diverge from the original, which points at
  prefill chunking, but a same-shape comparison was not run.
- Why continued checkpoints skip frontiers: read from the code
  (exact-multiple test), not traced at run time.
- The token-by-token mixed prefill in batched mode: inferred from the log
  (per-token chunk lines, 200 full-layer loads in the run) and the timing;
  the code path was not read in full.
- DSpark misses per token: estimated from drive reads (validated against
  `D8_STEP` within 1% on plain turns only).
- The attention/indexer share of the decode slow-down at 128k: an estimate
  (step time minus misses × 1.44 ms).
- Q2 is a contrast at 32k only.
- Repeatability: each long scenario ran once. The S4 probes repeat the first
  two turns six times with identical replies and decode within 0.5%.
