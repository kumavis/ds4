# D15: can returning experts be predicted? And the Q8-pipe floating-point-order switch

Branch `d12-cache-policy` in `/data/ds4-d12`; scripts `scripts/d15/`, results
`scripts/d15/out/`. Part A is simulation only, on the 13 D12 traces
(`/data/ds4-bench/d12-traces/`, simulator `scripts/d12/sim.py`). Part B is GPU work
on the d12 binary (built from bdf9396; later commits change only scripts
and docs). Queue log: `/data/ds4-bench/d15-queue.log`. Estimates are
marked as estimates.

## Bottom line

* **A. History does not predict which experts come back well enough to
  approach Belady.**
  * Learned and history-based policies are all worse than LRU or within noise in the steady state:
    * Hawkeye/OPTgen: +2 % median, worse on 12 of 13 traces.
    * Hawkeye with shared signatures: +3 %.
    * Predicted next use from the expert's own reuse history: +6 %, or +200-300 % without the overdue rule.
    * Co-occurrence bumping: -0.3 to -0.6 %.
  * None meets the bar. S3-FIFO (D12) stays the best realizable policy: -8 % median, ≥ 5 % on 9 of 13 traces.
  * **Ceiling for history.** An oracle given each expert's true reuse-distance distribution (future
    included, independent per expert) reaches -18 % median (-3 to -47 %) against Belady's -55 to -63 %.
  * **Ceiling for router scores.** An oracle that knows every selection 1 / 4 / 16
    tokens ahead gets only -1 to -2 / -2 to -5 / -7 to -14 %. Reaching -25 to -33 % needs 64 tokens ahead, and -35 to -49 % needs 128.
  * **Why.** Returning experts come back 130-290 tokens later (median), just past the
    cache's reach. Neither their own history nor near-term router knowledge
    sees that far.
  * **Recommendation.** Router-informed *eviction* is not worth a trace. The router's value is for
    prefetch (D5), not eviction. The trace that would test it is specified in §A.5.
* **B. `DS4_ROCM_C1_Q8_PIPE=1` changes the output and gives no measurable speed.**
  * Plain MXFP4 is -2.7 to +0.6 % (code -0.6, prose -2.7, hash +0.6, long +0.6) and Q2 code is -0.3 %.
  * The compute part, after removing the read time of the different text, is -0.3 to +0.5 ms per token.
  * The C1 profiler gives 64.97 ms (off) vs 65.15 ms (on) of non-read time per token.
  * DSpark +1.7 / +3.4 % comes from the different text (code 133/379 rounds/accepted vs 172/340), not from faster compute.
  * Tokens first differ at generated token 3 (code), 108 (prose), 18 (hash) and 112 (long), 0-based. Q2 code also differs at token 3.
  * Teacher-forced along the off run:
    * code: 99.2 % argmax agreement, 4 flips (flip margins ≤ 0.17);
    * prose: 97.7 %, 12 flips (margins ≤ 1.85);
    * mean of per-position max |Δlogit|: 1.58 (code) and 1.54 (prose); maximum 11.5 and 18.5.
  * **Recommendation: do not keep it as a labelled option.** It costs a different output
    and buys nothing measurable. Leave it off, or delete it.
* **Labels and gates.**
  * All 23 switch-on runs carry `output_class` fp-order, and no switch-off run does.
  * Every plain switch-on run has `ref_match` false. Every plain switch-off run has `ref_match` true with `ref_line` fork; all six references were reproduced.
  * The DSpark, profiler and forced runs have no reference key, so their `ref_match` is None.

Reading the table:

* **Distance.** Returns come back 130-290 tokens later (median). In per-layer terms that is a median
  stack distance of 134-161, against about 118 slots per layer: they are near misses.
  25-60 % more cache would catch most of them, as the D12 slot curves showed.
* **Concentration** is weak. 4,300-9,800 distinct experts return, each about 1.2-1.4 times on average.
  The top 10 % of them carry only 17-20 % of returns, and the top 10 of 40 layers carry 32-38 %
  (25 % would be uniform). There is no small hot set to pin.
* **Own-history predictability** is moderate. The rank correlation of consecutive
  log reuse distances of one expert is 0.36-0.52. The next distance lies within 2x of the
  previous one in 46-57 % of cases, against 29-38 % for a random pairing.
* **Clustering** is weak:
  * A return in layer L raises the chance of a return in layer L+1 of
    the same step from 0.18-0.67 to 0.30-0.75 (×1.1-1.9).
  * Co-selected partners do not return together. A partner's return rate (0.03-0.09) is about the base rate
    (0.04-0.11). The DSpark json and translate cases (n = 29 and 40) are too few to read.

### A.2 Policies: change in misses per generated token against LRU

These are realizable unless marked. The bar: at least 5 % fewer steady-state misses on most traces, none worse by more than 1 %, and warm-up not worse by more than a few percent.
Policy definitions are in the `policies.py` docstring. In short:

* **hawkeye:** OPTgen replays Belady on the past and trains a 3-bit per-expert counter;
  cache-averse experts are evicted first.
* **hawkeye-sig:** counters are shared by the signature (lookup count, log2 last reuse distance).
* **pnu:** evict the furthest predicted next use, where next use = last lookup + EWMA of the expert's reuse distances.
* **pnu-od:** the same, but overdue experts go first.
* **co-same / co-next:** after each call, bump the top same-layer partners, or the top next-layer followers, to MRU.
* **renewal:** an ORACLE (see A.3).

**Why the learned policies fail.**

* **Hawkeye.** OPTgen labels most past intervals as OPT misses, because a 130-290-token
  reuse exceeds what the cache can cover. Per-expert counters then see about one return each, too few
  to learn from. Shared signatures generalise no better.
* **PNU.** Predicting the next use from the previous distance keeps experts
  whose predicted time has passed, and those pollute the cache. Evicting overdue experts first fixes the
  pollution but is still worse than LRU.

### A.3 What bounds a history-only policy

There is no exact bound for "any function of the past". Two oracle models,
built in `policies.py` and simulated on all traces, bracket it:

* **`renewal` (per-expert statistics oracle).**
  * The policy knows each expert's true reuse-distance distribution, including the future, but not
    when the next lookup comes. It evicts the expert with the largest expected time to its next
    lookup given its age.
  * This is the best possible policy among those that treat each expert as an independent renewal process with
    perfectly learned statistics, which is the information a per-expert history
    policy is trying to learn.
  * Result: -3 to -47 %, median -18.5 %, steady. Its warm-up is up to +32 % worse, from evicting seeded experts.
  * Part of its gain is from knowing how many times an expert will
    *ever* return. That is future information, so the realizable ceiling is lower.
  * The pooled version, one distribution for all experts (`renewal-g`), is
    exactly LRU (±0 %): age alone carries no more than recency.
* **`look:h` (limited-horizon oracle).**
  * The policy knows every lookup in the next h token positions, perfectly, and nothing beyond. It falls back
    to LRU outside the horizon.
  * This bounds router-informed eviction, which at
    best sees the current token's later layers (h = 0) or a few drafted tokens (h ≈ 1-5).

**Conclusion.**

* The 55-63 % Belady gap is made of knowledge about lookups 50-300 tokens ahead.
* Per-expert history caps out somewhere below about -18 % (the oracle statistics). Realizable history gets about -8 % (S3-FIFO).
* Knowing the router's actual choices a few tokens ahead is worth only 1-5 % for
  eviction, and even a perfect 16-token view is worth 7-14 %.
* So the remaining gap needs neither more history nor
  near-term router scores. It would need a predictor of which experts the text will need
  in 100+ tokens: topic-level structure, which no tested signal shows.

### A.4 Is the router worth tracing?

* **For eviction: no** (A.3). Even a perfect 4-token view is worth at most 2-5 %.
* **For prefetch:** possibly. 15-53 % of decode misses are first use, and D5 already
  finds 37-40 % of misses with an early-router probe at +3 % tok/s.

### A.5 The trace that would test router-informed eviction or prefetch (not added)

**What to record.** Per routed layer, per single-token step and per verify row:

* the six selected expert ids with their selection scores (sqrt(softplus(logit)) + bias, the value top-k ranks);
* the next 16 non-selected experts by score: id (2 bytes) and score as fp16 (2 bytes).

**Volume.** That is 22 entries × 4 bytes × 40 layers ≈ 3.5 KB per token binary, about 1.8 MB per
512-token run, 7 MB per 2k run. As compact text it would be about 3x that.

**Capture.** Without a device sync:

* The scores already exist on the GPU at selection (`b->route_probs`).
* Copy the top-22 slice per layer into a device ring with one
  stream-ordered `cudaMemcpyAsync` per layer, the way D11's drafter trace does.
* Read it back once per token after the step's existing sync.

**Cost (estimate).** About 40 small device copies per token, likely
under 0.3 ms per token, plus one 3.5 KB readback. Output must be unchanged (gate:
digests).

**First use of it.** Measure AUC: does "ranked 7-22 at token t" predict "selected
within the next N tokens", against the base rate? Then simulate:

* protecting near-miss experts from eviction;
* a prefetch of the top-ranked non-selected expert.

The A.3 horizon bound says eviction cannot gain more than about 5 % at a 4-token view.

### B.3 Labels (`outclass.py` fields)

* **Switch-on runs.** All 23 (smoke, pairs, tf, fr, tfx, prof) have `output_class` fp-order.
* **Switch-off runs.** None has fp-order. The plain ones are `plain` and the DSpark ones `dspark-fast`.
* **`ref_match` on switch-on runs.** It is false for every switch-on run with a reference: 8- and 64-token smoke, code, prose, hash, long, Q2 code and fr/tf.
* **`ref_match` on switch-off runs.** It is true, with `ref_line` fork, for every plain switch-off run with a reference: code, prose, hash and long ×2, Q2 code ×2, and both refs.
* **No reference key.** For DSpark runs, the 128-token profiler runs and the forced DSpark-exact runs, `ref_match` is None.

### B.4 Recommendation

**Do not keep `DS4_ROCM_C1_Q8_PIPE` as a labelled option.**

* It changes tokens from the third generated token on every prompt tested, including Q2.
* It moves logits by about 1.5 per position on average.
* Its measured compute effect is within ±0.5 ms per token (0.5 %), with no sign of a gain.
* The tok/s differences in either direction (-2.7 to +3.4 %) come from the text it
  produces, not from speed.

Delete it or leave it off; it is not worth carrying a label for.

## Deviations

* **Teacher forcing.** The plain CLI decode ignores `DS4_D0_FORCE`: `d15-q8-tf-code` and `-prose` record `div_forced`
  false and are identical to the free runs. I added `q2.sh`, which repeats the forced
  runs as DSpark with `--dspark-verify exact` (bit-identical to plain decode per D0
  and int2). This is how `int2-gate-mx-code-exact-tf` was run.
  * These are `d15-q8-tfx-*`. Their tok/s (7.42, 8.39) is DSpark-exact speed, not comparable.
  * The forced reference is plain, as in int2.
* **Profiler.** Coarse mode reports no GPU time, so the "GPU time saved" is the non-read
  host-span difference.
* **Free-run divergence** is also available from the paired runs: their first differing token is listed in B.1.
  The `fr-*` runs were redundant with the pairs. They would have been the first cut had
  the queue run past 6 hours; it finished in about 6.9 hours plus 0.3 hours for `q2.sh`.
* **Restart.** The Mac restarted mid-task. The Part A scripts were rewritten from the same
  design, re-run, and gave the same numbers as before the restart.
* **Part A boundaries.** Part A uses the D12 traces, single runs per prompt. `co-*` learn partners
  from step and verify rows in the trace only.
