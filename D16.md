# D16: cache-conditional routing (Cache-Prior), exploration

Branch `d16-cache-routing`, worktree `/data/ds4-d16`, from `kumanix-int3`
bd19dab. The measured binary is 94ed082. Queue scripts are in `scripts/d16/`,
the log is `/data/ds4-bench/d16-queue.log`, and every number comes from
`/data/ds4-bench/results.jsonl` (`scripts/d16/table.py`).

**Status: exploration, off by default.** The switch is
`DS4_ROCM_ROUTE_CACHE_PRIOR=<lambda>`, default 0. Any run with lambda > 0
changes the output on purpose, and every such run here is labelled
`DS4_OUTPUT_CLASS=approx-routing` (all their records carry it). Nothing below
measures model ability. Divergence from the unmodified routing is reported;
quality is not claimed.

**Speed.** The recipe reports +22 to +30% without DSpark and +12 to +19% with
it, and misses down 52 to 73%. Here:
- Plain decode: +19% to +26%.
- DSpark: +27% and +45%. The DSpark gain is larger than the recipe's because
  acceptance also changed (387 against 340 accepted drafts at 0.09). So it is
  an end-to-end number on a different text, not an isolated I/O saving.
- Speed saturates past about 0.09: 0.2 adds 2 points over 0.09 while the
  output leaves the reference sooner.

**How far outputs move.**
- Every lambda > 0 run leaves the reference text within its first 11 to 213
  generated tokens.
- After that point the texts differ, so the positional token match is low:
  0.03 to 0.16 on code, 0.45 on long.
- Even before the first differing token the logits are not close: the largest
  absolute logit difference over the common prefix is 3.9 to 6.8. No
  position is bit-identical.
- Swaps only ever drop unbiased ranks 4-6, as keep 3 guarantees. Rank 6 is
  dropped most often.
- The weight share of the dropped exact picks ("drift") averages 4.2% to 6.1%
  per row-layer.
- The first differing position is not monotone in lambda on DSpark (11 at
  0.05, 213 at 0.09). Where the texts part depends on one small-margin flip:
  the reference top-1 to top-2 logit gap at the first flip was 0.23 and 0.16.

**Repeatability at a fixed slot count.** Two lambda 0.09 plain code runs
(separate processes, 4730 slots) gave identical tokens: 983db0a4a5bb/511 both
times, with identical swap counts (8214 row-layers). The 64-token smoke at
0.09 matched the first 63 tokens of both.

## What is implemented (commits 26bf47a, c9f7eae, beaf545, 94ed082)

**Selection** (`rocm/ds4_rocm_router.cuh`, `route_prior_kernel`).
- The unmodified router kernel runs first and is untouched.
- With lambda > 0, a second kernel then re-selects the same rows, following
  the recipe's `route()`:
  - `c = s + bias` with `s = sqrt(softplus(logit))` (the first kernel's
    probs);
  - `r_obs = max(c) - min(c)`;
  - `R = Rbar[layer]` if > 0, else `r_obs`;
  - `+lambda*R` for experts resident in the transaction's snapshot or in the
    unbiased top-keep (the first kernel's first `keep` picks);
  - top-6 with ties to the lower index;
  - weights from the unbiased `s` of the picks, normalised and scaled by the
    same expression as the unmodified kernel.
- Per row and layer, the kernel also records `r_obs`, which unbiased ranks
  were dropped, and the drift.
- At lambda 0 the second kernel is never launched and no snapshot is taken.

**Transactions** (ds4.c, host side).
- **Plain decode step:** a decode step (`ds41_graph_step` with a logits
  buffer, outside a verify round) is one transaction. The residency snapshot
  is taken at the step start for all 40 layers, so evictions by earlier
  layers of the same step do not change later layers' masks. Its row's ranges
  commit to Rbar at the step end.
- **Verify round (DSpark):** one transaction per round. A single snapshot
  taken when the round opens is used for every row and layer of the round,
  for both batched (fast) and scalar (exact) verification. The round's
  speculative reads therefore cannot change its own rows' routes. Only the
  rows the round commits (`ds41_draft_rollback`'s accepted count) add their
  ranges to Rbar; rejected rows are discarded.
- **Snapshot:** a 40 x 384 mask built from the SSD expert cache's resident
  list for the target model (about 0.03 ms per transaction, an estimate from
  the list length), uploaded with the frozen Rbar before the routers that use
  it.
- **Rbar:** per layer, the mean of the committed rows' `r_obs`. It is 0 until
  a committed row exists; a row then uses its own range.

**Not biased:**
- Prefill. Both layer-major prefill and prompt tokens stepped one at a time
  route unbiased, and prefill ranges do not feed Rbar.
- The DSpark drafter's own routing. Its 128 experts are all resident, so
  there is nothing to bias, and the recipe gives the drafter no rule.
- Image rows in verify.
- TP (two-GPU tensor parallel).

**Counters (printed at exit):**
- per mode (decode rows; verify committed rows): rows, row-layers, row-layers
  with a swap, swapped picks, dropped unbiased ranks 1-6, mean drift;
- verify rounds, verified rows, verify batch misses, mean snapshot size.

### Where I had to interpret the recipe

1. **Prefill.** The recipe also biases prefill against residency frozen at
   the call's start. I left prefill unbiased: the brief allowed it, and a cold
   process has an empty cache, so the recipe's first prefill is a no-op
   anyway. Prefill ranges are also not added to Rbar, although the recipe
   counts prefill rows as committed.
2. **Eviction policy.** The recipe pairs the routing with its own eviction:
   popularity EMA, near-pick credit and pinning. ds4 keeps its existing cache
   policy. Under biased routing, eviction decides which experts the model is
   allowed to use, so the miss and drift numbers here belong to ds4's policy,
   not the recipe's.
3. **Snapshot timing.** The recipe snapshots "when the round opens". I took
   the plain decode snapshot once per token, for all layers, not per layer
   just before each router.
4. **Exact verify** shares one snapshot per round (scalar rows), like the
   batched verifier. It was gated only at lambda 0.
5. **D5 prefetch** (off by default) still predicts unbiased routes. The recipe
   requires a read-ahead to predict the biased routes. It is untested
   together with lambda > 0.

## The first lambda 0.09 smoke failure, and the fixes

Builds and fixes before the measured binary:
- **26bf47a** did not compile: per-layer arrays at file scope were sized by
  `DS4_N_LAYER`, which is not a constant.
- **c9f7eae** fixed that.
- **c9f7eae's lambda 0.09 smoke** (`d16-smoke-mx-l09-64`, the earlier "STOP
  after d16-smoke-mx-l09-64 (exit)") failed in prefill at position 0. The
  session's prefill steps prompt tokens one at a time through
  `ds41_graph_step`, so a transaction opened for a prefill row and the apply
  call refused its arguments. **beaf545** opens a transaction only for steps
  that produce logits (decode), so prefill rows stay unbiased, and makes the
  apply call print why it refuses.
- **beaf545's smoke** then failed at the first decode step (position 94) with
  `D16 apply: bad arguments (... expert=384 ...)`. The code used
  `DS4_ROCM_N_EXPERT`, which is 256 (DeepSeek V4's expert count); V4.1 needs
  `DS4_ROCM_MAX_N_EXPERT` (384). The same constant had sized the residency
  mask's stride and its expert filter: the failed run's mean snapshot held
  3097 experts instead of 4730.
- **94ed082** switched the D16 block to 384 throughout. Its smokes passed, and
  every number in this document is from 94ed082.

## Setup

- **Fixed cache sizes:** `--ssd-streaming-cache-experts` 4730 dynamic slots
  for plain and 4260 for DSpark. These are the counts the memory-sized cache
  chose on int3 for those modes (plain 4703-4743, DSpark 4240-4273). The run
  logs confirm "4730 experts" and "4260".
- **Prompts:** code with `--nothink` (512 tokens) and the 1.4k-token long
  prompt (256 tokens).
- **DSpark:** fast verify with the old scheduler (the default).
- **Logits logs:** every sweep run writes one. lambda 0 runs are the
  references (`DS4_D0_LOGITS=auto`), and lambda > 0 runs carry
  `DS4_REF_TAG=<lambda 0 run>`, giving free-run divergence fields.
- **Teacher-forced runs:** none; see the deviations.

## Deviations from the brief

The original brief's sweep was cut to the coordinator's revised scope when
the queue paced at 40-55 minutes per run:
- No prose or json prompts.
- No lambda 0.1 or keep 2 runs.
- Two runs only at lambda 0.09 plain code; one run at every other point.
- DSpark at the two lambda values chosen from the plain curve (0.09 and 0.05)
  instead of the full sweep.
- No teacher-forced runs, so there are no teacher-forced agreement or flip
  statistics over whole runs. Divergence comes from the free runs only (first
  divergence, common-prefix argmax agreement and logit differences, positional
  token match).
- No Q2 pair.
- Of the lambda 0 gates, these ran: -n 8, -n 64, code 512, long 256, DSpark
  172/340 and exact verify. Prose, hash and Q2 code did not run again; the
  lambda 0 path launches nothing new.
- I added a full-length lambda 0.09 repeat and the exact-verify gate, because
  the queue went faster than expected in the end.

## Not verified

- Model quality of any lambda > 0 output: out of scope.
- Behaviour with a full cache over long sessions. These runs start from a
  fresh process, with the cache warming during the run.
- Interaction with D5 prefetch.
- Multi-session batches.
- Image rows.
- Repeatability under the memory-sized cache. The slot count varies run to
  run there, so outputs at lambda > 0 are expected to vary; that is not
  measured.
- Any routing unit test separate from the GPU runs. Its correctness evidence
  is: identical results on two runs; dropped ranks never 1-3 with keep 3 (as
  required); lambda 0 bit-identical. The routing has no model-free test.
