## Part A: KV checkpoints that agent sessions hit

### What was wrong (from the code and D14)
- **Exact multiples only.** The stock rule stores a "continued" checkpoint
  only when the live position equals an exact multiple of the 10,240-token
  interval (`ds4_kvstore_continued_store_target`). It is checked at prefill
  progress points, at prompt end and at every decode step.
- **Prefill checks never succeed on V4.1.** A layer-major prefill has no
  stageable checkpoint until its chunk has finished; measured, every attempt
  logs `kv cache skipped ... session has no valid checkpoint to stage`. So
  in practice a checkpoint was written only when a multiple fell inside a
  generated reply: 3 in D14's 132k session.

### The change (`ds4_server.c`; switch `DS4_KV_TURN_CHECKPOINTS=1`, off by default)
- **Turn end.** After the final response is sent (in `generate_job`, off the
  time-to-first-token path), store the whole live state if at least T tokens
  were added since this slot's last store. T is the continued interval
  rounded to `--kv-cache-boundary-align-tokens`, or
  `DS4_KV_TURN_CHECKPOINT_MIN_TOKENS` (unaligned) when set.
- **No other stores in this mode:** none from the decode loop (the turn end
  covers the reply) and none mid-prefill (they cannot work on V4.1, see
  above).
- **Same storage path.** Stores use the same kvstore path with reason
  `continued`, so files, budget and eviction ranking are unchanged. A log
  line `kv cache turn checkpoint tokens=N ms` records each one.
- **Off means stock.** Switch off, the stock rule runs unchanged.
- **Files.** Functions: `kv_cache_maybe_store_continued_at` (new; the old
  name wraps it), `kv_cache_turn_target_step`, `kv_cache_turn_step`,
  `kv_turn_checkpoints`, `kv_cache_turn_min_tokens`,
  `kv_cache_store_turn_end`, and one call in `generate_job`.
- **Tests.** Server unit tests pass (`ds4_test --server`); the build is
  clean.

**Restore is bit-exact.** Restored at the same position, with the same
suffix (so the same prefill chunking), the reply is token-for-token
identical to the uninterrupted session's: 256 of 256 at ~102k. The earlier
divergences (D14, and the rows above that restore one or more turns back)
come from prefilling a different span, so the chunk boundaries move, not
from the disk restore.

**Cost.**
- Checkpoint saves after a turn: 34-292 ms at 12k-31k, 1.04 s at 102k
  (633 MiB). They come after the response, so they do not touch TTFT or
  decode.
- Size: ~6.2 MiB per 1k tokens.
- At one checkpoint per turn in a 100k session, the 32 GB budget's eviction
  keeps roughly the last 40-50.

**Outputs.** Replies are identical with the switch on and off. The off,
on and on-2k sessions have the same `replies_digest` (19e4805724a1e6df), so
`DS4_OUTPUT_CLASS=exact`.

**Drive heat.** The hot drive is `nvme0`, the 2 TB system drive holding the
MXFP4 replica under `/home`: 87-88 C in the long sessions. The data drive
`nvme1` reached 84 C. There is no sign of throttling: in heavy-read samples
(prefill sweeps) read throughput rises with temperature (both are driven by
the reads), up to ~12 GB/s total at 86-88 C, and `nvme0`'s share stays
0.47-0.49 in every temperature bucket (`heat.py`, 823 samples). Only 3
samples reached 88 C, so this says nothing above that.

**Recommendation.** Turn the switch on with
`DS4_KV_TURN_CHECKPOINT_MIN_TOKENS` around 512, so there is a checkpoint at
every turn end. With the driver's token-identical history normalization
(next section), a restart then costs about one turn's prefill.

**Committed rule, clean ds4 code (3d43e27; the record's dirty flag is set only by a harness script).**
- The `d17-a2-*` rows above are the committed rule. The `d17-a-*` rows used the first patch state (bd19dab, dirty), which also made mid-prefill attempts. Every one of those attempts failed with "no valid checkpoint to stage" and stored nothing.
- With the same settings, the two rules store the same checkpoints. The 102k headline (`d17-a-on2k-100k-*`, interval 2,048) is therefore valid for the committed binary and was not rerun.
- On the committed binary: the off twin restores in 127.7 s (126.1 s on the first binary), and every-turn checkpoints restore in 80.7 s against 78.4 s uninterrupted. The replies match the off twin on every turn (`twin_reply_match` true for 9 of 9).

**Default threshold (after these runs).** With `DS4_KV_TURN_CHECKPOINTS=1` and no `DS4_KV_TURN_CHECKPOINT_MIN_TOKENS`, a checkpoint is stored at every turn end that adds at least `--kv-cache-min-tokens` (512 by default). That is the measured `d17-a2-on512` configuration. The code change is two lines, syntax-checked; it is built and unit-tested with the Part B tree.

**Disk cost at that default** (from D14's real turn ends, ~6.2 MiB per 1k tokens):

| Session to | Turns (checkpoints) | Bytes written | Last file |
|---|---|---|---|
| 32k | 9 | 1.1 GiB | 192 MiB |
| 64k | 24 | 5.9 GiB | 396 MiB |
| 100k | 40 | 13.8 GiB | 612 MiB |
| 132k | 56 | 25.0 GiB | 818 MiB |

Measured at 31k: 7 checkpoints (two turns added under 512 tokens), 31-187 ms each, 0.9 GiB written.

**Eviction** (`ds4_kvstore_entry_eviction_score`):
- Nothing is evicted until the budget is exceeded, so one 100k session's 40 files (13.8 GiB) all stay within 32 GB.
- Once the budget is exceeded, the lowest score goes first. The score is (decayed hits + 1) × tokens per byte; cold, evict and shutdown checkpoints get an anchor factor.
- A continued checkpoint whose text is a prefix of the one being written is marked down, so a session's own older turn checkpoints are evicted first.
- With several sessions sharing the directory, each session's newest checkpoint competes on hits and recency, and superseded ones go first. Two 100k sessions (~28 GiB) still fit; a third starts evicting the oldest superseded files.
- Only the newest checkpoint per session is needed to resume. A later option could delete a slot's previous turn checkpoint when it writes the next one: one file per session (~0.6 GiB at 100k) instead of ~40. Not built.
- Writes are small next to the reads: 13.8 GiB per 100k session, against ~216 GiB read by every prefill sweep.

**Output class vocabulary.** From these runs on, `output_class` uses `/data/ds4-env/outclass.py`'s names. A declared `DS4_OUTPUT_CLASS` wins; otherwise it is derived as `plain` or `dspark-<verify>`. Part A runs are `plain`. The per-turn comparison against the off twin is separate (`twin_identical_tokens`, `twin_reply_match`). The early `d17-a-*` records carry the legacy label "exact", meaning `plain`.

## Special-token text inside user and tool content (for upstream, not patched)

When ds4 tokenizes a rendered chat prompt (`tokenize_rendered_chat_vocab` ->
`special_token_at` in `ds4.c`), it matches a fixed table of special-token
spellings anywhere in the text, including inside user messages and tool
results. On DeepSeek V4.1 that table includes the ASCII spellings of other
model families' markers:

| Text | Becomes |
|---|---|
| `<\|user\|>` | V4.1 `<｜User｜>` |
| `<\|assistant\|>` | `<｜Assistant｜>` |
| `[gMASK]` | the BOS token |

`<think>`, `</think>` and others map to their tokens too, where the
vocabulary has them.

**Reproduction.** Model-free: `--dump-tokens` reads only the tokenizer from
the GGUF. The file `/data/ds4-bench/d17-specialtok.txt` holds this text,
without a trailing newline:

```
<｜begin▁of▁sentence｜><｜User｜>Tool output: printf("<|user|>"); x = "[gMASK]"; y = "<|assistant|>";<｜Assistant｜></think>
```

```
./ds4 -m DeepSeek-V4.1-Flash-1017-MXFP4-experts.gguf --dump-tokens --prompt-file d17-specialtok.txt
```

gives (kumanix-int3 bd19dab):

```
     0  <｜begin▁of▁sentence｜>
128803  <｜User｜>
 42639  Tool
  5238  Ġoutput
    28  :
 13128  Ġprintf
  1698  ("
128803  <｜User｜>        <- the text "<|user|>" inside the user message
 30839  ");
  1527  Ġx
   438  Ġ=
   582  Ġ"
     0  <｜begin▁of▁sentence｜>   <- the text "[gMASK]"
 21390  ";
   383  Ġy
   438  Ġ=
   582  Ġ"
128804  <｜Assistant｜>   <- the text "<|assistant|>"
 21390  ";
128804  <｜Assistant｜>
128822  </think>
```

**Consequences.**
1. **Role injection.** A tool result that contains these strings (source
   code of a tokenizer, a chat template, a log) puts real role or BOS tokens
   into the model's input.
2. **Disk KV misses.** The disk KV cache keys a checkpoint by the decoded
   token text (`<｜User｜>`), while the client resends the original text
   (`<|user|>`). The SHA-1 of the request's prefix then never matches a
   checkpoint taken after such a string. In D14 this cut the restorable
   history of a 66k session to 30,720 tokens.

The D14/D17 driver works around (2) only, by rewriting these spellings in
the replayed history to the canonical form. The token IDs are identical, so
the model input is the same. Nothing in ds4 was changed.

**Possible upstream fixes.**
- Match special tokens only at template positions: the renderer knows where
  it put them; content could be tokenized as plain text.
- Or key disk checkpoints by token IDs, or by the rendered request text,
  rather than by the decoded token text.

## Part B: design (written before building; results follow in "Part B results")

The union-loading sweep is the main lever; the one-sweep path for 2-8k appends and the token-major threshold come after it.

### Today's append dispatch and the one-sweep path

How a V4.1 append is cut into prefill calls today, on ROCm
(`ds41_prefill_count` in `ds4.c`, kumanix-int3):

| Append (new tokens) | ROCm today | Cost seen in D14 |
|---|---|---|
| < 256 (`minimum`) | token-major: one decode-like step per token, on the warm decode cache | ~0.14 s per token (99 tokens 13.7 s, 184 tokens 23.5 s) |
| 256-2,048 | one layer sweep of the whole append | ~20 s fixed + a little per token |
| 2,049-4,095 | a 2,048 sweep, then a sweep (or token-major steps) for the rest | 2 passes |
| 4,096-8,191 | the wide (carry) path in multiples of 2,048, then the tail | 2 passes (e.g. 4,356 = 4,096 + 260) |
| larger | wide path up to `carry_cap` (32,768 seen), then the tail | 96-122 tok/s |

**The one-sweep path for 2-8k appends.**
- It was added upstream in e9e1baa ("Process medium CUDA SSD appends in
  one layer sweep", 2026-09-14), already inside
  `#if !defined(__APPLE__) && !defined(DS4_ROCM_BUILD)`.
- Conditions: SSD streaming, one GPU, `prefill_cap >= 2048`,
  `carry_cap >= remaining`, `2048 < remaining < 8192`, and a final tile of
  at least 256 rows. The whole append then goes in one sweep, keeping the
  2,048-row arithmetic partitions.
- The upstream commit reports full logits, caches, snapshots and next
  decode exact through 60k context on CUDA, and a 3,241-token prefill going
  from ~55 to ~98 tok/s.
- Nothing in the history says the path failed on ROCm. It was written and
  validated on CUDA, and ROCm and Apple were left on the old dispatch.
- On ROCm the same carry workspace already serves the wide path (`>= 4096`,
  multiples of 2,048), so the building blocks exist there.
- The upstream test `tests/test_deepseek41_prefill.c` (`check_dispatch` and
  the model-backed `check_mixed`, which compares logits, caches and next
  decode with the path on against a control with it off) is the gate to
  port to ROCm.

**Plan.**
1. Switch `DS4_ROCM_V41_MEDIUM_SWEEP=1` (off by default) enables the
   medium-sweep condition on ROCm; the CUDA kill switch stays.
2. Port the test checks for ROCm: dispatch, plus `check_mixed` with the
   switch against the control on a real model (under the lock, from
   int4).
3. A same-binary off/on pair: a 32k session with the switch, and one 100k
   confirmation. Record `twin_identical_tokens` and declare
   `DS4_OUTPUT_CLASS`: `exact` if every reply equals the off twin's,
   otherwise `fp-order`, since the arithmetic partitions are the same by
   design.

**Small appends.**
- On ROCm a sweep below 256 tokens is never used; above it, always.
- Measured costs: token-major ~0.14 s per token, a sweep ~20 s. So the
  crossover is about 140-150 tokens (estimate, from D14 turns). Appends of
  150-255 tokens currently take the slower path.
- A "routed experts only" sweep: with 384 routed experts per layer and 6
  per token, uniform routing touches 63% of a layer's experts at 64 tokens,
  86% at 128 and 98% at 256 (estimate). The sweep already copies the cached
  ~28% device-to-device. So a routed-only sweep could save at most ~30-40%
  of the reads, and only below ~200 tokens, where token-major is already
  close. Not worth building before the threshold is tuned.
- Plan: switch `DS4_ROCM_V41_TOKEN_MAJOR_MAX=N` to replace `minimum`.
  Measure appends of fixed sizes (32, 64, 128, 192, 256, 384, 512 tokens)
  at a fixed fill with N=1 (always sweep) and N=1024 (token-major up to
  1,023), each on its own server session restored from a turn checkpoint.
  The crossover is where the two TTFT curves meet.
- Output class: token-major and sweep take different arithmetic paths for
  the same tokens. The decode path uses prequantized Q8 activations
  (`DS4_ROCM_Q8_PREQUANT_DECODE`), so this would be `approx-q8act`, not
  just fp-order, unless the code says otherwise. To be read and stated
  before running.

### Union-loading sweep (the main Part B lever; design as written before building)

**Today.** D16's trace and the code agree: before a layer's router runs,
the whole layer (384 experts) is put into the two-layer staging. Residents
are copied device-to-device and everything else is read from the drives,
about 12,300 experts (~216 GiB) per chunk whatever its size.
- `ds41_stream_layer_enter(il)` joins the reader for layer `il` and starts
  the whole-layer read of `il+1`, so that read overlaps layer `il`'s
  compute.
- The prefill MoE gets the staging base pointers and indexes them by
  expert ID (`cuda_stream_layer_expert_cache_apply`), so only routed
  experts' slots are read.

**Union mode** (switch `DS4_ROCM_V41_UNION_SWEEP=<max rows>`, off by
default; only for warm chunks up to that size; whole-layer loading stays
the fallback):
1. At layer `il`: attention, then the router (`ds41_route_batch`,
   unchanged).
2. Read the selected IDs back (as `ds41_prefill_seed` does) and form the
   union.
3. Prepare a plan with a wanted mask: residents in the union are copied
   device-to-device; non-resident union experts are read.
4. Run the MoE.

Routing is unchanged and the same experts' bytes are used, so the replies
should be token-identical to the whole-layer path. That is to be shown with
an off twin, and the off/on switch is the fallback.

**How much speculation can overlap** (`spec.c` on D16's trace
`d16b-trace-s1.bin`, offline). Per layer, warm chunks:

| Chunk rows (mean) | Union / 384 | Need (union not resident) | Prev chunk's union: covers / extra reads | Hot-128: covers / extra |
|---|---|---|---|---|
| <=512 (258) | 182 | 91 | 79% / 82 | 44% / 18 |
| 513-1,023 (742) | 229 | 128 | 88% / 59 | 36% / 9 |
| 1,024-2,048 (1,857) | 274 | 168 | 76% / 31 | 32% / 4 |

- The need at ~258 rows (91 per layer, ~3,640 per chunk) matches D16's
  3,656.
- Speculating with the previous chunk's union for the same layer covers
  76-88% of the needed reads, at the price of 31-82 unneeded reads per
  layer. Each layer's historically hottest experts are mostly resident
  already, so they cover little.

**Time model** (estimates; read rate ~11 GiB/s, from D14 sweeps of ~216 GiB
in ~20 s):
- **Small chunks (~256 rows).** Union serial is ~1.6 GiB per layer ≈ 0.15 s,
  plus the layer's compute. If compute is ~50 ms per layer, that is ~8 s per
  chunk against ~20 s today. Speculation would add more reads (~154 per
  layer) than the overlap saves, so plain union first.
- **Large chunks (~1.9k rows).** Compute per layer is longer, so a serial
  union read (~0.27 s per layer) adds up. Speculating with the previous
  union (~159 reads per layer, overlapped), then a serial top-up of ~40,
  should come out about level with whole-layer loading. The crossover is
  set by per-layer prefill compute time, which I have not measured.
- **Plan.** Measure per-layer compute first (one run with union mode at
  several fixed chunk sizes), then set the default `max rows` at the
  crossover, then decide on speculation.

**Measurements planned** (int4, once its gates pass):
- appends of ~256, 1-2k and 2-4k tokens at 32k, 64k and 100k fill, each as
  an off/on pair on one binary, restored from turn checkpoints (Part A
  makes the restores cheap);
- token identity against the off twin, `output_class`;
- one 100k confirmation;
- the prefill share of session time.

**The two switches** (both in `ds41_graph_prefill_sweep` in `ds4.c`; the
Metal names are historical, and both work on ROCm):
- `DS4_METAL_GRAPH_PREFILL_PROFILE=1` prints, per layer and chunk,
  `ds4: V4.1 prefill layer= pos= rows= ... map= engram= encode= drain= seed= ms`.
  - `map` is the wait for the expert loader.
  - On ROCm, `encode` does not wait for the GPU and `drain` is 0, because
    the commands are not active there. The layer's GPU time therefore shows
    up in `seed`, whose read-back synchronizes.
- `DS4_METAL_V41_STAGE_PROFILE=1` adds `ds4: V4.1 stage layer= pos= rows= <stage>= ms`.
  Every stage (`hc/engram`, `attention projections`,
  `attention core/index`, `attention output`, `hc/ffn norm`,
  `shared/routed ffn`, `hc expand`) ends with
  `ds4_gpu_end_commands`, which is `cudaDeviceSynchronize` on ROCm. Each
  stage's time is therefore its own GPU time, and `seed` is only the seed.
  The synchronizations add a little: TTFT was within ~1% of the
  unprofiled run.

sweeps are compute-bound: the whole-layer read is already hidden behind
~20-23 s of FFN per 2,048 rows. Merging a 2-8k append into one sweep would
save only the loader wait of the extra sweep (≤1.2 s here) and a few
hundred milliseconds of fixed per-layer cost. Not worth a change on its
own.


## Part B results (kumanix-int4 6a48b38 + Part A, branch `d17b-prefill-union`)

### Step 1: what a prefill sweep spends its time on
See the per-stage table in the D20 section above.
- From ~1k rows a sweep is **compute-bound**: the expert FFN alone is
  ~60%, and the whole-layer read is hidden behind compute.
- Below ~500 rows the visible cost is the **loader wait**: 5-11 s per sweep
  at 256-533 rows. Union loading can only win there.

### Step 2: union-loading sweep (`DS4_ROCM_V41_UNION_SWEEP=<max rows>`)

**What it does.** For a sweep of at most `<max rows>` (<=2,048, one
sub-chunk), no layer is read whole ahead of time. After each layer's
router, the routed IDs are read back, resident experts in the union are
copied into the staging, the rest are read, and then the expert FFN runs
as before. Routing, the experts' bytes and the kernels are unchanged.

**Exact.** Replies are token-identical to the whole-layer path on every
turn:
- `d17-b1-dev-union-grow` (max 2,048): 9 of 9 turns against
  `d17-b0-prof-grow`;
- `d17-b3-dev-union512-grow` (max 512): 6 of 6 turns compared against
  `d17-b2-stageprof-grow`.
- Gated twins on one binary: see "Gates" below.

### Item 4: partial staging reclaim for union sweeps: built, failed the gate, withdrawn

**Idea.** D13 lends the 768 staging slots to the expert cache between
sweeps. At every sweep start after decode, it reclaims them all: 768
entries that decode had just loaded are evicted.
- Measured: 145 union reads per layer for a 256-row sweep after decode,
  against 67 for a 260-row sweep without decode before it.
- The idea was to keep the staging lent during a union sweep and take back
  only the slots each layer's union needs (switch
  `DS4_ROCM_STREAM_STAGING_RECLAIM_UNION`; commit 6aa474f; reverted).

**Failure.**
- Gate session `d17-b5-grow-union-partial` against `d17-b5-grow-whole`,
  same binary.
- Turns 0-4 were token-identical. Turn 1's partial union sweep ran with no
  lent entries resident.
- Turn 5, the first union sweep after decode had filled the lent slots
  (768 resident, all evicted), diverged after 27 tokens. Every later turn
  diverged too.
- **The records of that session from turn 5 on are invalid.**

**Cause: a wrong slot mapping (mine).**
- The staging is planar: 384 gate blocks, then 384 up blocks, then 384
  down blocks. Expert `e` occupies three separate pieces.
- A lent slot `j` is a contiguous block `[j × slot_bytes, (j+1) × slot_bytes)`.
- The patch treated "union expert `e`" and "lent slot `e`" as the same
  memory. The union load therefore wrote into lent slots that still held
  live cache entries (decode's experts), and decode then read those
  corrupted weights.
- The violation counter (0 throughout) checked the wrong mapping.

**Why it is not fixed.**
- Correctly mapped, each lent slot overlaps about three experts of one
  plane.
- With a union of about half the experts (180-260 of 384 at 256 rows), a
  slot can stay lent only if none of its ~3 experts is routed: about
  0.48³ ≈ 11% of slots (estimate).
- So a union sweep must reclaim nearly the whole staging anyway, and the
  extra reads after decode cannot be recovered this way.

**Containment.**
- The queued 100k run that would have used the switch was stopped while
  waiting.
- The driver refuses to send requests when the switch is set (flag file
  `/data/ds4-bench/d17-skip-reclaim-union`).
- Nothing persisted beyond the server process: no disk KV in that
  session, and the corruption was in that process's GPU memory.

**Lesson for anything that lends or reclaims staging memory (D13, D19).**
Map through the planar layout. D13's full reclaim is correct because it
takes all 768 slots back.

**What would recover the after-decode reads instead** (not built; for the
owner and D19):
- Lend the staging as planar-aware slots, so a slot is one expert's three
  pieces. That needs the cache's slot shape to differ from the staging's,
  so it is not possible without changing the cache's slot layout.
- Or seed less after warm sweeps (D19). Seeding refills ~114 experts per
  layer per sweep, which displaces what decode needs; the post-decode
  union reads would then hit more cached experts.

## Activation precision: decode against prefill on ROCm (finding; no new runs)

Stock ROCm V4.1 runs the same dense Q8_0 weights at two activation
precisions, depending on the path a token takes.

**Decode, and token-major prefill.** Token-major prefill runs decode
steps, so it gets the same treatment.
- The dense Q8_0 matvecs use activations prequantized to 8 bits
  (`DS4_ROCM_Q8_PREQUANT_DECODE`).
- The flag is on by default: `cuda_runtime_config` in
  `rocm/ds4_rocm_runtime.cuh` sets `q8_prequant_decode = !g_quality_mode && (env unset || env present)`,
  with the comment "Prequantized Q8 decode kernels are substantially
  faster on gfx1151. Quality mode retains the full-F32 activation path,
  and an explicit =0 remains available as a diagnostic rollback."

**Layer-sweep prefill.** `ds41_matmul_batch` in `ds4.c` runs Q8_0 and F16
projections through the full-tile WMMA path, whose own comment says it
"uses F16 operands internally". The activations are therefore 16-bit;
outputs are rounded to BF16 where the graph asks.

**Quality mode.**
- Selected with `--quality` on `ds4` (`ds4_cli.c`) and on `ds4-server`
  (`ds4_server.c`). The help text is "Prefer exact kernels where faster
  approximate paths exist."
- The engine option `quality` reaches the runtime through
  `ds4_gpu_set_quality` into `g_quality_mode`.
- In quality mode decode keeps F32 activations. It also changes other
  kernel choices in the same block: split-K attention output, the fused
  shared gate/up, the cuBLAS attention output and the shared down
  projection.

**Our records.**
- No benchmark record has used `--quality`: 0 lines with it in
  `results.jsonl` or `sessions.jsonl`.
- None sets `DS4_ROCM_Q8_PREQUANT_DECODE` either.
- So every decode figure in this project (single prompts and sessions) ran
  with 8-bit activations in the dense decode matvecs, and every prefill
  with 16-bit activations in the sweep.

**Why it matters here.** `DS4_ROCM_V41_TOKEN_MAJOR_MAX` moves appends
between these two paths, so it changes outputs through activation
precision, not only evaluation order. Its output class is
`approx-prefill-dispatch`. The same holds for anything else that moves
tokens between decode steps and sweeps: stock's own fixed 256 threshold,
and DSpark verify rows taking batched paths. That is not investigated
here.
