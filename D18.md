# D18: the expert cache in agent sessions

Branch `d18-session-cache` (from `d12-cache-policy` 4a3075b), worktree
`/data/ds4-d18`. Scripts are in `scripts/d18/`, tables and JSON in
`scripts/d18/out/`, traces in `/data/ds4-bench/d18-traces/`, and session
records in `/data/ds4-bench/sessions.jsonl` (tags `d18-s1-plain-trace-a` and `-b`).

The run is one plain MXFP4 agent session, two drives, D14 payload v2,
`--ctx 163840`, through `ds4-server`. It ran in two server sessions as in D14 part A:
0 → 66k with disk KV saves, then a clean stop, restore at 66k, and growth to 98.8k.

Estimates are marked: every tok/s or ms gain below is *modelled* at 1.44 ms per miss
unless it says measured.

* **Bound.** Belady at the same slot count: 13.12 (−58.7 %).
* **The single changes do not add up.** #1 + #2 measures −26.7 % together. Fixing the refill matters
  more than keeping experts.

**Do the single-prompt conclusions carry over? Yes, all three.**

* **S3-FIFO about −8 %** (D12, steady state): it carries over and is larger in a session, −14.5 %
  overall. The steady part is −8 to −13 %, as in D12. The first 16 reply tokens are −30 to −52 %, because the
  small FIFO keeps the sweep's seeds from flushing decode's working set.
* **Belady headroom** (−55 to −63 %): carries over, −58.7 %. The steady part is 12-14 against
  26-33 misses per token.
* **Returns at 130-290 tokens** (D15): carries over. Returning experts come back a median
  117-119 decode tokens later (p25 74-80, p75 201-206, p90 348-380). 39-46 % of
  returns cross a turn boundary.
* **History-only ceilings** behave the same as in D15: the 16-token lookahead oracle reaches −12 % (D15: −7 to −14 %) and 64 tokens reach −31 %.

**Why misses rise with context: it is decode's own working set, not the slots.**

* After the first 16 reply tokens, misses go 26.1 → 28.2 → 30.6 → 32.6 per token
  at ~16k → 32k → 64k → 100k.
* Almost all of the rise (+7.2 of +6.5; the other causes fall slightly) is experts evicted by
  decode itself. The distinct experts a reply touches in its tokens 16-79 grow from 3,860 to 4,347 (+13 %),
  against a fixed 4,577-4,596-slot cache.
* Slots do not change during a session; the cache is sized once at startup for `--ctx`.
* The sweep's refill accounts for 30-49 of the 53-62 misses per token in the first 16 reply tokens. The cost
  takes about 64 tokens to decay: 71 misses/token at tokens 0-3, 39 at token 16, 28 at token 56, 26 at token 64.

**Non-read step time grows little in the session.**

* Measured in the session: +2.4 ms from ~16k to ~100k (68.1 → 70.5 ms). The step grows +12.1 ms (120.6 → 132.7), and
  read wait accounts for +9.7 ms of it (80 %).
* The C1 events profiles place the context-dependent compute in the indexer
  top-k (+2.0 ms from a 2k to a 30k prompt), the rope/KV write (+1.3), the attention output (+1.2)
  and the HC norm (+0.9). The attention core is flat.

## 1. Trace

* **The D12 switch works under `ds4-server`.** It already distinguishes sweep chunks (P marks)
  from single-token steps (S). It could not tell token-major prompt steps (appends ≤ ~40 tokens) from decode, and it had no turn boundaries.
* **Added (trace only, 64e6288).** `ds4_session_sync` writes a Q mark before each prompt sync
  (checkpoint length, prompt length) and a q mark after it. Lookups between Q and q are prefill; S steps after q
  are decode.
* **Gates on the new build, trace off.** Code 8 / 64 / 512 tokens give b1cd778da121/7, 3098d05a1cef/63 and
  8290541d324b/511. Trace on, 64 tokens: 3098d05a1cef/63, with Q/q present. All pass.
* **The session.** 40 turns, 51 sweep chunks, 10,290 decode tokens and 449k cache calls.
  * The replay of the runtime's LRU reproduces every hit, miss and victim of both halves: 0 mismatches, evictions always at
    4,577 or 4,596 resident.
  * Decode misses per token match D14's int2 session: rest 26.1 → 32.6 here, 26.5 → 35.7 there at 128k.
* **The restored second half** starts from an empty cache. Its first turn is left out of the fill buckets.

* **(a) More distinct experts.** The rise is here. Decode-caused misses go +7.2 per token from 16k to 100k, while
  the distinct-expert count of a reply grows 13 %. One session cannot separate
  "longer context" from "later, more varied content"; both grow together here.
* **(b) Slots.** None are lost during a session. The plan is fixed at startup (4,577 and 4,596 in the two
  halves; D14's 4,649 → 4,550 is across `--ctx` sizes).
* **(c) Each sweep.**
  * Its end-of-layer refill (`ds41_prefill_seed`, top budget/40 experts per layer, led
    by the last 32 prompt tokens) replaces most of the cache. That causes 30-49 of the 53-62 misses per token
    in the first 16 reply tokens, and still about 6 per token later in the reply.
  * Recovery by reply position (misses per token): 71 (tokens 0-3), 53, 53, 47, 39 (16), 42, 40, 37, 36, 31 (40) …
    28 (56-63), 26 (64), then 26-31.
* **(d) Token-major prompt steps** (short appends) are a small cause: up to 2 per token at 64k.

## 3. Policies on the session (simulated)

**Rules** (same as D12):
* Every lookup inserts.
* The call's protected set is never evicted.
* Seeds are the runtime's own refill calls: device copies that evict but are not counted as reads.
* "Sweep reads" is Σ over sweep layers of (384 − experts of that layer resident when the sweep reached it). That is
  what the sweep's D2D reuse saves; each read is one expert at full bandwidth (≈1.44 ms).

**Variants:**
* `keep:N`: the N most recently used experts at the start of a turn's prompt cannot be evicted until
  the prompt is done.
* `seed:n`: only the first n of each layer's refill list (the runtime's priority order) are inserted.
* `seed:cold`: full refill only for a layer holding under half its share.
* `d13`: +768 slots between sweeps, with the physical slots tracked (LIFO free list, lent buffers on top) and every
  staging-resident entry evicted at each sweep, as D13 reclaims.

**Reading it:**

* **Retention curve (for D17).**
  * Almost nothing up to N = 1,024, −1.8 % at 2,048 and −4.5 % at 3,072, all in
    the first 64 reply tokens.
  * It costs the sweep 3-10 % more expert reads at N = 512-2,048. The protected experts force the
    refill to evict other layers' experts that the next chunk would have reused.
  * It costs token-major prompt steps 1-22 % more misses.
  * Retention only pays when it holds most of the cache. At that point it is just "do not refill".
* **The refill is the lever.**
  * Without it, the first 16 reply tokens miss 25-41 instead of 53-62 per token.
  * The sweeps also read 8-9 % fewer experts, because the decode working set that the refill
    used to flush also serves the next sweep's D2D reuse.
  * The refill does earn its keep on a cold cache: the first turn, or after a restart; in D12, dropping it cost +39-66 % warm-up misses.
  * `seed:cold` keeps it there: same decode misses as no refill, and 4k fewer prompt-step misses.
* **Belady + seed:0 is worse than Belady.** Placed optimally, the refill's experts are useful. It is LRU's
  handling (refill experts enter as most recent) that makes them harmful. S3-FIFO handles them better on its own:
  its first-16 count falls from 62 to 43 at 16k, and to 29 at 32k.
* **D13's reclaim at each sweep** costs only 0.8 points against keeping the 768 slots for good. Retention
  on top of D13 adds 0.6 points.

## 4. The non-read part

* **Session, measured (D8_STEP).** Non-read time per step is 66.3 / 68.1 / 68.5 / 69.6 / 70.5 ms at ~8k /
  16k / 32k / 64k / 100k. The fit gives +0.036 ms per 1k positions, so about +3.6 ms per 100k. Of
  the +12.1 ms step growth from 16k to 100k, +2.4 ms is non-read and +9.7 ms is read wait.
  D14 estimated ~6 ms non-read at 128k; this fit gives ~4 ms there (estimate).
* **Which stage.** The C1 events profiler (`DS4_ROCM_C1_PROF=events`, CLI, 64 decode tokens after a
  2k / 8k / 30k prompt; tags `d18-c1ev-ps-*`), GPU ms per token:

| segment | 2k | 8k | 30k | 2k → 30k |
|---|---:|---:|---:|---:|
| indexer q/proj/scores + top-k | 1.03 | 1.53 | 3.00 | +1.97 |
| attn rope + KV write | 0.59 | 0.59 | 1.90 | +1.31 |
| attention output (attn_out) | 15.86 | 15.83 | 17.03 | +1.17 |
| HC norm | 4.17 | 4.18 | 5.03 | +0.86 |
| HC pre / layer pre | 0.88 | 0.88 | 1.40 | +0.52 |
| attention core | 4.49 | 4.48 | 4.54 | +0.05 |
| compressor | 0.42 | 0.42 | 0.42 | 0 |
| step minus read wait | 78.9 | 79.4 | 85.6 | +6.7 |

* **The indexer is the clearest context-dependent cost.** The growth in the HC norm, attn_out and
  rope segments is time between null-stream events: work queued earlier
  (KV and compressor writes) can land there, so their split is approximate.
* **The CLI points grow faster than the session** (+6.7 ms over 2k → 30k, against +4.2 ms over 8k → 100k in the
  session's host-side non-read). The two methods differ: GPU events against host span minus host read wait, with reads
  overlapped by D2. The CLI runs also decode only 64 tokens right after a fresh prefill. Measurement
  only; no kernel was changed.

## Deviations

* **Trace change.** I added the Q/q marks (trace only, gated as asked). The session goes to 98.8k, not 100k: the
  driver stops at the turn that crosses its target.
* **Turn count.** D14's payload turns were larger in this run than D14's medians suggest: 26 turns to 66k.
* **C1 runs.** Three short C1 events runs (CLI, about 25 min of lock) were added for item 4's stage split.
* **D13.** The D13 interaction is simulated (slot-level model of lend and reclaim), not traced. The int4
  traced session waits for your go.
* **Refill variants.** "Refill from the experts the last prompt tokens routed to": the trace has the
  refill's priority list (led by the last 32 prompt tokens) but not per-token routing, so the
  variants are top-n of that list and refill-when-cold. Refilling from exactly the last K tokens was
  not simulated.
* **Drive temperature.** Both server sessions reached 88 °C on the hottest NVMe (throttle at 89). MemAvailable minimum was
  13,141 and 13,453 MiB (floor 12,288).

## Not verified

* **One session, one payload seed.** A single session cannot separate content drift from context length in cause (a).
* **Nothing built.** All policy numbers are simulated misses. The tok/s figures use the miss-cost
  model; the model does not include the sweep-read savings in decode tok/s.
* **Combinations.** S3-FIFO together with D13 was not simulated.
* **Restore.** The restored half's cold start is excluded from the fill buckets but is part of the
  whole-session totals.
* **Profiles.** The C1 stage split comes from CLI runs, not from the server session.
