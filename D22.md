# D22 session memory

## Function ownership

The implementation commit ba73af6 owns the DSpark runtime charge in ds41_mem_cache_plan_compute, admission arithmetic shared by ds41_memory_admit_for_host and ds4_admit.h, the memory guard sampler and sweep hooks, and polling at synchronization and ordinary/speculative token boundaries in ds4.c. Engine open/close manage the sampler. ds4_gpu.h and the ROCm compatibility/runtime headers expose and implement safe cache slab release and staging reclamation. The model-free test is tests/test_d22_admit.c. The queue scripts are later commits.

## Scope and evidence

Branch `d22-session-memory` (handover head `20e0104`). Of the 18 short benchmark records, ten recorded checkout head `d12f025` and eight recorded `20e0104`. The intervening commit changed only the queue 2 pause check. Report 46's per-turn log analysis found that after the first ~20k tokens system memory mapped by the GPU was effectively flat through 132k plain and 98.6k DSpark. DSpark settled approximately 500 MiB lower than plain. Roughly 170 MiB of the difference appeared in GPU-mapped memory. Startup sizing varied by about 200 MiB and DSpark prefill sometimes consumed another 100–250 MiB temporarily.

The branch charges DSpark runtime at startup and can release expert cache slabs under pressure at a quiescent point. The rollback switch is `DS4_ROCM_STREAM_MEM_GUARD=0`. Historical model-free admission test output records PASS (0 failing) for injected host sizes, including admission at N and refusal at N+1. The runtime gate requested 6,000 dynamic expert slots. Host-RAM sizing fitted the request to 5,757 slots (100.80 GiB). Admission then required 121.70 GiB including reserves against 121.42 GiB available and exited 1 before decode. The observed 0.28 GiB refusal margin depends on host state.

## Attended pressure trial

The driver held 383 MiB between turns in `d22-s1-pressure`, allocating
256 MiB and then 127 MiB. With six samples below the 13,056 MiB guard
line, decode poll 473 freed an allocated 35-slot slab. Available memory
rose from 12,952 to 13,586 MiB while the pages remained held. This
was the only pressure check and the only slab release.

Four turns completed while the driver held those pages for about five
minutes. It returned the full 383 MiB at the planned release step, and
two more turns completed. Together with two pre-hold turns, all eight
completed successfully, with 2,060 raw reply positions and a final fill
of 26,531. The guard sampled a low of 12,940 MiB, 652 MiB above the
project floor. The two-second system sampler saw 12,941 MiB and a peak
NVMe temperature of 85 °C. The server shut down cleanly after 747 s.
The hold log, raw server events, turns and driver summary were verified
on the host and again from the local archive.

## Long-session proof procedure

Run each mode as a separate user unit on the exclusive GPU lock, with a fresh server and an empty dedicated disk KV directory. Use payload v2, `--ctx 163840`, a 134,000-token grow target, a 32,768 MiB disk KV budget, and a 200-minute turn-admission budget. Run DSpark first with the old scheduler, then plain after the DSpark result has been checked. Both use automatic cache sizing and the D22 guard.

Require one continuous session from an uncached first turn through at least 131,072 actual tokens. Check every HTTP outcome, the final fill, process and host memory samples, NVMe temperatures, guard activity, final shutdown checkpoint and the driver's single SIGTERM after the server is idle. For DSpark, verify accepted drafts at long context. Keep the proposed guard default under review until both proof runs have been measured.
