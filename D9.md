# D9: DSpark round economics (width, when to draft, drafter cost)

Branch `d9-dspark-economics` in `/data/ds4-d9`, started from `kumanix-int`
(6e69e59). Build 1 = 22bbaae (traces, probe, scheduler), build 2 = 40a9237
(fitted scheduler defaults). Model MXFP4 unless stated; 512 tokens; `--nothink`
on code only; harness `/data/ds4-env/bench.sh`; queue logs
`/data/ds4-bench/d9-queue.log`. Scripts: `scripts/d9/`.

## Bottom line

* **The schedule is not the limit; the drafter's acceptance prediction and
  the reads are.** An oracle that knows how many drafts each round will accept
  is 25.7 % above the old scheduler (modelled, mean of five prompts: 12.91 vs
  10.31 tok/s). A scheduler that sees only the drafter's confidences gets at
  most about +6 % of that (+3.7 % with fixed constants). The remaining ~20
  points need a better acceptance predictor (drafter quality), not a better
  schedule.
* **New `DS4_DSPARK_SCHED=model`** (deterministic cost model, no clock input;
  runs repeat exactly: identical rounds, accepted drafts and misses in r1 and
  r2). Teacher-forced along the plain text (every scheduler verifies against
  the same tokens, the clean comparison): **+3.8 % over old on average**
  (code +3.8, prose +1.6, json +7.1, translate +4.5, list +1.9 %); online
  +3.2 %. Free-running (fast verify drifts to a different text per
  scheduler): +0.4 % on average (code +4.8, prose +2.0, json -1.0,
  translate -4.7, list +1.0 %); the json and translate losses come from the
  different text and its cache behaviour, not from the schedule (section 5).
  Q2 code: 14.59 vs 14.25 (+2.4 %), online 14.69. Default unchanged (online).
* **Reads dominate a round.** verify ms = 77 + 14 x rows + 1.37 x misses
  (R^2 0.995); misses are ~25 per verified row with no sharing between rows,
  so each extra row costs ~14 ms compute + ~38 ms read wait. Modelled: the
  oracle with zero read wait is 28.7 tok/s, with half the read wait 17.8.
* **Drafter: 20.2 ms per proposal, flat in width** (all five positions are
  one batch): stages 11.5, vocabulary head 5.4, Markov chain 3.2, readback
  0.01. Nothing cut: the only sizeable proposal-preserving cut (vocab head,
  ~3 ms, estimate) shares its kernel with the verifier and would have to be
  bit-identical; the drafter is ~6 % of round time, so the whole item is
  worth ~1 % (estimate).
* Gates pass: plain digests unchanged (MXFP4 8290541d324b / 511, Q2
  f0a2cd53a247 / 511), and `--dspark-verify exact` under `model` equals plain
  on code and prose (511/511, logits bit-exact).
* Side finding for the cache owners: a plain step inside a DSpark session
  costs ~125-135 ms vs 118 ms in plain decode (code), from ~37 % more expert
  misses (the 8 GiB resident drafter shrinks the expert cache from 4,947 to
  3,719 experts). That is why DSpark cannot match plain on prose and list.

## 1. Per-round data

### New switches (all off by default, read by no decision except the probe)

| switch | what |
|---|---|
| `DS4_D9_ROUND_TRACE=1` | one `D9_ROUND` line per DSpark round, every scheduler: `pos`, `mode` (old/online/model/probe), `why`, `proposed`, width `k`, `matched`, `kept`, `seed`, the 5 drafted token ids, the 5 drafter confidence logits (hex, exact), `prop_ms` (drafter), `verify_ms`, `commit_ms`, `plain_ms` (plain step), `total_ms`, and the stream-cache counters the round moved (`slots`, `misses` = decode-path misses, `jobs`, `wait_ms` = read wait). Expert misses of a verify round = `jobs / 3` (the decode-path `misses` counter does not see verify rows). |
| `DS4_D9_PROBE=1` | draft at every draftable position, log the full proposal, then take a plain step (width forced to 0). The run follows the plain greedy trajectory, and gives the drafter's 5-token proposal and confidences at every position. |
| `DS4_DSPARK_SCHED=model` | the new scheduler (section 3). |

What the code exposes as drafter confidence is the DSpark confidence head: a
logit per drafted position (`sigmoid` = predicted probability that this draft
is accepted given the earlier ones were). The drafter's own token
probabilities/margins are not read back (they would cost a 5 x 129k readback);
I did not add that.

| rows | n | verify ms | misses | misses/row | read wait ms | non-read ms |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 958 | 169.6 | 46.6 | 23.3 | 81.6 | 88.0 |
| 3 | 492 | 221.5 | 74.4 | 24.8 | 125.7 | 95.8 |
| 4 | 403 | 274.8 | 103.8 | 26.0 | 172.0 | 102.9 |

| 6 | 242 | 379.0 | 158.2 | 26.4 | 253.3 | 125.7 |

So time is almost exactly linear in rows and misses, and misses are
proportional to rows (about 25 per row, no sharing between the rows of one
verify: the experts a verify row misses are mostly ones no other row needs).
Each extra verified row costs about 14 ms of compute plus about 35-47 ms of
read wait. That read cost per row is the main limit: a row costs 40-45 % of a
whole plain step, so a draft must be accepted with probability above about
0.45 (at the plain rate; higher at the DSpark rate) just to pay for itself.

Misses per row vary by prompt (cache hit rate), so the replay uses per-prompt
constants, from the probe's plain steps and each prompt's verify rounds:

| prompt | P plain ms | of which read wait | D drafter | misses/row | V(rows) ms |
|---|---:|---:|---:|---:|---|
| code | 125.2 | 58.4 | 20.2 | 30.8 | 77.2 + 56.3 r |
| prose | 116.7 | 48.5 | 19.8 | 25.5 | 77.2 + 49.1 r |
| json | 118.1 | 49.1 | 20.0 | 21.7 | 77.2 + 43.8 r |
| translate | 117.0 | 47.9 | 19.9 | 23.4 | 77.2 + 46.3 r |
| list | 111.3 | 41.8 | 19.7 | 25.0 | 77.2 + 48.4 r |
| Q2 code | 86.9 | 20.5 | 20.3 | 8.9 | 65.7 + 41.2 r (Q2 fit: 65.7 + 26.6 rows + 1.644 misses, R^2 0.985) |

A plain step inside a DSpark session is slower than a plain-decode step: code
125-133 ms vs 118.3 ms in `int-mx-code-plain-r1`. Read wait per miss is the
same (about 1.8 ms); the session has more misses per step (code 38.8 in the
old run's plain steps vs 28.4 in plain decode at similar positions), because
the resident drafter (8.04 GiB) shrinks the expert cache from 4,947 to 3,719
dynamic experts and the verify rows churn it. This is why DSpark cannot reach
plain speed on prose and list by taking plain steps: every plain step in the
session costs ~5-12 % more than outside it. (Read side / cache size: not
changed here, noted for the owners.)

(`d9-probe-old-traj-mx-translate`) it gives 11.15 (220 rounds, 292 accepted)
against 11.70 (176, 336): there the drafter, fed single-step features in the
probe instead of verify-row features, proposes slightly differently. The
teacher-forced measurements in section 5 confirm the replay's policy ranking:
model/old +3.8 % measured vs +3.7 % replayed.

### What the headroom says

* **Scheduling with this drafter's confidence: about +4-6 %.** The oracle is
  25 % above the old policy (modelled mean 12.91 vs 10.31), but a policy that
  only sees the drafter's confidences gets 10.70 (+3.8 %) with fixed
  constants, and at most 10.93 (+6 %) even with per-prompt costs and a free
  look at the confidences before paying for the drafter. The other ~19 points
  of the oracle's gain need knowing which drafts will be accepted, which the
  confidence head does not tell well enough (section 1). **The limit is the
  drafter's acceptance prediction, not the schedule.**
* **Drafter quality.** With every draft accepted (`perfect`), 15.5 tok/s; the
  oracle reaches 12.9 because A[p] is low on prose/list (mean 1.4) and
  moderate on json/translate.
* **Reads.** The oracle with zero read wait is 28.7 tok/s, with half the read
  wait 17.8; even the old policy with zero read wait would be 21.3. Reads
  remain the largest single factor for DSpark: each verified row brings ~25
  misses (~38 ms of wait), so overlap/caching work on the read side moves
  DSpark more than any scheduling change.
* Fixed widths are all worse than old on average (best fixed2 9.60); always
  drafting with the old width rule (`no-plain`) is +1.8 % over old.

## 3. Scheduler `DS4_DSPARK_SCHED=model`

Deterministic: every decision is a function of the token stream (drafted
tokens, their confidence logits, accepted counts), never of a clock or a
cache counter, so a run repeats exactly. `old` and `online` are unchanged and
`online` stays the default.

* Costs (ms, env-settable): P plain step, D drafter, V(r) = VA + VB r.
  Defaults by routed expert type, from the fit above: MXFP4 P=118 D=20
  V=77+49r (pooled over the five prompts); other types (Q2) P=87 D=20
  V=66+41r (Q2 code).
* Acceptance: p_i = sigmoid(CAL_SCALE x confidence_i + bias_i); defaults
  scale 1, bias 0 (raw head: the fitted calibration gave no replay gain).
  Optional ETA nudges bias_i toward observed acceptance (default 0).
* Width, after the drafter ran: k in 0..MAX_WIDTH maximising
  E(k) - rho C(k), E(k) = 1 + sum_i prod_{j<=i} p_j, C(0) = P,
  C(k) = V(k+1), rho = KAPPA / P (KAPPA 1.1: an extra token must repay its
  time at 1.1 x the plain rate).
* Draft or plain step, before the drafter: EWMA (HALFLIFE 1 round) of the
  predicted advantage over plain, adv = (E(k) - 1) - (D + C(k) - P) / P. Below
  GATE (-0.1) the next SKIP (8) rounds are plain steps, then one probe
  proposal restarts the average; consecutive failed probes double SKIP up to
  SKIP_MAX (64).
* Env: `DS4_DSPARK_MODEL_{P,D,VA,VB,KAPPA,CAL_SCALE,CAL_BIAS,ETA,HALFLIFE,
  GATE,SKIP,SKIP_MAX,MAX_WIDTH,SIGNAL}`; the chosen constants are printed at
  start (`ds4: DSpark model scheduler ...`) and a summary at the end
  (`ds4: DSpark model sched final ...`).
* Tuning: grid over KAPPA, calibration, HALFLIFE, GATE, SKIP, SKIP_MAX,
  SIGNAL, ETA (`scripts/d9/tune.py`); the objective was the mean of modelled
  model/old over the five prompts. The top of the grid is a flat plateau
  (+4.2-4.5 %); leave-one-prompt-out choices score within 0.1 tok/s of the
  all-prompt choice on code/json/translate and +0.5-1 % on prose/list, so the
  constants are not tuned to one prompt, but the replay gain is small
  everywhere.

## 4. Drafter cost

Profile, 108 proposals on code (`d9-drafter-prof-mx-code`, sync-bracketed,
medians, ms):

| part | ms |
|---|---:|
| setup (embeddings, writes) | 0.11 |
| stage 0 / 1 / 2 (5 rows each) | 3.86 / 3.93 / 3.68 |
| - attention output (F16 grouped) | 3.67 (3 stages) |
| - routed experts | 3.81 |
| - attention projections | 1.50 |
| - shared expert | 1.12 |
| - attention | 0.56 |
| - pre-norm / after-attention / router / tail | 0.30 / 0.29 / 0.09 / 0.06 |
| collapse + norm | 0.03 |
| vocabulary head (Q8_0, 5 rows) | 5.43 |
| Markov chain (5 sequential steps, F32 rank-256 head) | 3.18 |
| readback of tokens + confidences | 0.01 |
| total | 20.23 (unprofiled mean 20.06) |

Plus per committed token: 0.86 ms of drafter KV bookkeeping inside each plain
step (`pend_ms`) and 0.3 ms per verify commit.

The proposal computes all five positions in one batch, so there is no real
per-drafted-token cost: drafting 1 or 5 tokens costs the same 20 ms. Sampling
is the GPU Markov argmax; host readback is 0.01 ms.

What could be cut without changing proposals (estimates, none implemented):

* Vocabulary head, 5.43 ms: 563 MB of Q8_0 in 5.43 ms is about 104 GB/s
  against 241 GB/s measured peak, so about -3 ms is possible (estimate). It
  is the same `ds4_gpu_dsv41_q8_projection_rows` kernel the verifier uses for
  its head, so a faster kernel must be bit-identical per row or it changes the
  target's verify logits too; not attempted here.
* Markov chain, 3.18 ms: 5 x 132 MB of F32 transposed head at ~208 GB/s, at
  bandwidth already. Storing it as F16 would halve it (about -1.6 ms) but
  changes confidences and possibly tokens; that needs a yes under the
  accuracy policy and was not built.
* Stages, 11.5 ms: D8 already removed the per-row re-reads; what is left is
  near the weight-read floor for 5 rows (estimate).

Upper bound of the whole item: the drafter is about 6 % of round time (20 of
~330 ms); a 3 ms cut is about 1 % of decode time (estimate). The scheduler's
gating is the larger drafter saving: it skips proposals where they do not pay
(section 5, proposals per run).

`fast` verify each scheduler drifts off the plain text at some position

accounting of r1 (`D9_ROUND`): on json, model 191 rounds / 576 verified rows

at 47.4 s, measured 46.1 vs 45.8 s. On translate, model's verified rows

rows), which is the whole difference. On the shared text (teacher-forced),
model is ahead on all five prompts.

**Drift (`div_*`, owner's accepted near-tie drift).** Free runs: model leaves
the plain text at the same position as old on code, json, translate and list
(75, 37, 32, 78); on prose at 7 (online also 7; old 108), so its prose
tf_agree covers only 7 positions. Teacher-forced tf_agree (every position):

0.9667 / 0.9863 / 0.9863 / 0.9746 (code/prose/json/translate/list); all above
D0's 0.95. Drift tracks how many positions are verified in multi-row passes,
so it moves with the width mix, both up (list) and down (prose).

is high and skips proposals where the predicted advantage is negative: on
prose (free run) 112 proposals and 324 plain steps against old's 72 and 378;
on code 129 proposals against 108.

## 7. Not verified / limits

* **Replay is a model.** It replays on the plain text with one cost
  constant per prompt; the real fast-verify runs write different texts. It
  matches measured old within 1 % on json/prose/list and along the old run's
  own text on code; it is 5 % off on translate. The headroom numbers
  (oracle, fixed widths, zero/half read wait, perfect drafter) are modelled
  estimates; the zero/half read-wait columns in particular extrapolate the
  linear fit (read wait = 12.4 + 1.52 x misses) to a regime that was not
  measured.
* Teacher-forced comparison: one run per scheduler and prompt (run-to-run
  noise on repeated runs here is about +-0.1 tok/s, e.g. old code 10.76 /
  10.90). Free-running: two runs each, online once, as asked.
* Q2: only code, one run each; the Q2 model constants come from one prompt
  (code), so they are less certain than MXFP4's.
* The model scheduler's constants are fixed. Misses per row vary with the
  prompt (21.7-30.8) and with the cache state; the policy does not adapt to
  that (by design, to stay repeatable). A miss-count input would be
  deterministic only if the read path is, which I did not check.
* Drafter: breakdown measured with sync-bracketed profiling (adds
  synchronisation, total 20.23 vs 20.06 unprofiled); no cut implemented, so
  the "about -3 ms vocab head" and "about 1 % of decode" are estimates.
* Not done: a better acceptance predictor (it is where the remaining
  headroom is, ~+20 % modelled, but it is a drafter-quality change); reading
  back drafter token probabilities/margins (only the confidence head is
  traced).
* The default scheduler is unchanged (online). On the teacher-forced
  comparison model and online are within 1 % of each other on average
  (model ahead on json/translate, online on code/prose/list), and model
  repeats exactly; whether to make it the default is your call.
